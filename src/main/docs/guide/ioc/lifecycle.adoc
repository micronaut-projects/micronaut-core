=== Destruction Order

When the context is closed, singletons are destroyed in dependency order: a bean is always destroyed before the beans injected into it, whether they were injected through the constructor, a method or a field. This lets a bean use its dependencies from its `@PreDestroy` method.

Beans that are not injected into each other but still have to be created and destroyed in a particular order can declare the dependency with ann:context.annotation.DependsOn[]. The annotated bean is created after, and destroyed before, every bean of the listed types:

snippet::io.micronaut.docs.lifecycle.MessageConsumer,io.micronaut.docs.lifecycle.MessagePublisher[tags="class", indent=0]

<1> The consumer depends on the publisher without injecting it
<2> The consumer stops while the publisher is still open, so it can publish the messages it has in flight
<3> The publisher is closed once the consumer has stopped

The annotation also works on factory methods and accepts interfaces, in which case every bean implementing the interface is created before and destroyed after the annotated bean. Beans not connected by any dependency are destroyed in bean name order, so the destruction sequence is the same from run to run.

Bean destruction listeners are kept alive as long as the dependency order allows. Dependencies used by these listeners are destroyed after the listeners themselves.

TIP: Shutdown logic that spans several beans can also be placed in ann:runtime.event.annotation.EventListener[] methods for api:context.event.ShutdownEvent[], which is published before any bean is destroyed. Such methods can be ordered with ann:core.annotation.Order[].

== Dependent Beans

Dependent beans are the beans used in the construction of your bean.
If the dependent bean's scope is `@Prototype` or unknown, it will be destroyed along with your instance.

=== Resolving Dependencies After Construction

Inject api:context.BeanDependencyResolver[] when a managed bean needs to resolve dependencies dynamically and retain them for its own lifetime:

[source,java]
----
@Singleton
class Handler {
    private final BeanDependencyResolver dependencies;

    Handler(BeanDependencyResolver dependencies) {
        this.dependencies = dependencies;
    }

    Worker createWorker() {
        return dependencies.getBean(Worker.class);
    }
}
----

Each lookup follows the usual scope and qualifier rules. A newly created prototype belongs to the consumer, including its nested dependents. Core destroys these resources after the consumer's destruction callbacks, in reverse acquisition order. Resources acquired during construction are also cleaned up if construction fails. A failed lookup cleans up resources created by that lookup without releasing previous successful acquisitions.

Use `resolver.getBeanRegistration(type)` when you need the dependency's registration and bean definition as well as its instance. Overloads accept either `Class<T>` or `Argument<T>`, with an optional qualifier. These lookups retain the same ownership as `getBean(...)`; returning a registration does not transfer ownership to the caller. For early destruction of an owned dependency, resolve it through a dependency group and use `group.destroy(registration)`.

Singletons and custom-scoped beans remain owned by their scopes. Dynamically resolved dependencies participate in context shutdown ordering and destruction ordering in scopes based on `AbstractConcurrentCustomScope`, including those reached through a consumer's owned prototype interceptors. The resolver does not extend a custom scope's lifetime or prevent explicit destruction of a shared bean. Dependency cycles use the same deterministic cycle handling as injected dependencies.

The resolver can be used during construction and retained for later use. It must be injected into a managed consumer; it is unavailable through a standalone context lookup. As with other dependent resources, callers obtaining standalone prototypes should retain and close their api:context.BeanRegistration[]. Ordinary api:context.BeanContext[] and api:context.BeanProvider[] lookups keep their existing lifecycle behavior.

Once destruction of the consumer begins, only its own destruction callbacks, such as a `@PreDestroy` method, can still look up, on the destroying thread and until they return; what they create is destroyed with the consumer, after the callbacks. Once context shutdown begins, lookups are only accepted on the thread running the shutdown, on behalf of a api:context.event.ShutdownEvent[] listener or a destruction callback, and what they create is destroyed before the shutdown completes. Other lookups are rejected. A lookup racing destruction releases newly created dependents if it cannot attach them to the consumer. The resolver does not retain the consumer's construction path; do not use it to resolve the consumer recursively during construction.

==== Explicit dependency ownership

`BeanContext.createBeanRegistration(definition)` creates a fresh instance of an exact bean definition,
regardless of its declared scope, and returns a `CreatedBean` that retains its dependent instances.
Close the returned registration to destroy the instance and its dependents. It neither replaces nor removes
an existing scoped instance of the same definition. To create a contextual target behind a separate proxy,
pass the target definition.

`BeanContext.createDependencyGroup()` creates a caller-owned, `AutoCloseable` dependency group.
Its lookups respect scopes, retain newly created dependents, and leave shared beans owned by their scopes.
Use `group.destroy(registration)` for early destruction: it removes only a registration owned by that group,
using registration identity. `group.createBeanRegistration(definition)` creates a fresh owned instance.
A group returned by an injected `BeanDependencyResolver.createGroup()` also belongs to the consumer and is
closed automatically with it. Independent groups must be closed by their callers.

For temporary method arguments, `BeanContext.withDependencies(group -> ...)` releases owned dependencies
when the synchronous invocation ends, including when it fails. Cleanup attempts every dependent and suppresses
cleanup failures on the invocation's exception.

Once shutdown begins, new groups and fresh registrations can only be created by a `ShutdownEvent` listener, on the
thread publishing the event. Groups created earlier, independent or owned by a consumer, stay usable by the listeners
and destruction callbacks running on the shutdown thread. Whatever a group creates during shutdown is destroyed before
the shutdown completes, even if the group is never closed; what it held before remains the caller's to release.

A `BeanPreDestroyEventListener` that needs temporary dependencies while a bean is being destroyed calls
`event.withDependencies(group -> ...)`. These lookups are allowed during shutdown, only on the destruction
thread and until the listener returns; `BeanContext.withDependencies` itself is not available to a destruction
listener during shutdown. Do not return an owned dependency from either invocation, since it has already been destroyed.
