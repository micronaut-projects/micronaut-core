WARNING: The bean definition prefetch is experimental. It is off unless you switch it on, and it may change or go away in a later release.

Before an application started with `Micronaut.run(...)` reads its bean definitions, the main thread creates the application context builder and runs the `ApplicationContextConfigurer` services. The bean definition prefetch starts once logging is configured, reads the bean definitions on the common `ForkJoinPool` in the meantime, and hands them to the context that `Micronaut.run(...)` builds.

Switch it on with a JVM system property:

[source,bash]
----
java -Dmicronaut.bean-definitions.prefetch=true -jar application.jar
----

In a container, `JAVA_TOOL_OPTIONS` can carry the property. Only `true`, in any case, switches it on: any other value, or no value, leaves the prefetch off. It must be a system property of the JVM: the prefetch starts when the `Micronaut` class is initialized, before any configuration is read, so the property has no effect in `application.properties`, in an environment variable such as `MICRONAUT_BEAN_DEFINITIONS_PREFETCH` or in the builder's properties.

The prefetch calls the same provider that the context would call, so it reads the same bean definitions, and a bean definition whose static initializer fails stops the application as it does without the prefetch.

=== When it pays

The prefetch moves work off the main thread; it does not remove any. It pays only when other processors are idle while the main thread starts:

* It needs four or more processors. It stands down when the common pool has fewer than three threads, because Micronaut also uses the pool to load the bean definitions, and the main thread, which would otherwise help, then only waits. The pool size follows the processor count, which `-XX:ActiveProcessorCount` and container CPU limits change, and `-Djava.util.concurrent.ForkJoinPool.common.parallelism` sets it directly.
* It stands down in a native image.
* It is larger without a JDK AOT cache than with one, which already makes loading the bean definitions cheaper. Measure the startup of your application with and without the property before you keep it.

=== Caveats

* *Which contexts get it.* Only `Micronaut.run(...)` and `Micronaut.build(...).start()` hand the prefetched bean definitions over. A context from `ApplicationContext.run()` or `ApplicationContext.builder()`, `BeanContext.run()`, Picocli's `PicocliRunner` or a test framework gets nothing. If the `Micronaut` class is initialized but `start()` never runs, the work is wasted. A context built while the prefetch still runs reads the bean definitions beside it.
* *Code that runs earlier.* The static initializers of the bean definitions, of the `TypeConverterRegistrar` services and of the shared conversion service run on a pool thread, while the main thread creates the builder and runs the configurers. An initializer that depends on state set up in that window sees it unset. Logging is configured before the prefetch starts, so a logger that such an initializer creates is the logger it gets without the prefetch.
* *The conversion service.* Code that constructs `DefaultMutableConversionService` directly on the main thread between the initialization of `Micronaut` and `start()`, such as an `ApplicationContextConfigurer`, can deadlock with the prefetch. Use `MutableConversionService.create()` or `ConversionService.SHARED` there.
* *Late static optimizations.* A call to `StaticOptimizations.set(...)` after the `Micronaut` class is initialized can fail with "read before it was set", because the prefetch may already have read that optimization, for example `SoftServiceLoader.Optimizations` or `ClassUtils.Optimizations`. Micronaut AOT registers its optimizations through `StaticOptimizations.Loader` services, which the prefetch reads first, so it is not affected.
* *A replaced bean definitions provider.* A provider set with `ApplicationContextBuilder#beanDefinitionsProvider(...)`, by the application or by a configurer, wins, and the prefetched bean definitions are dropped. A provider that loads the bean definitions itself also loads them beside the prefetch.

If the prefetch was not handed to the context and it failed, Micronaut logs a warning that names the property. The context then read the bean definitions itself, and it may have skipped one whose initializer had already failed on the prefetch's thread, where without the prefetch that failure would have stopped the application. Start without the property to see Micronaut's own handling.
