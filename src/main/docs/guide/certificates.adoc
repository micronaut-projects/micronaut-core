[[certificates]]
== Certificate providers

Certificate providers let you externalize how TLS key and trust material is supplied to the framework. Each provider is a named bean and can be referenced from server and client SSL configuration using:

- `micronaut.server.ssl.key-name` / `micronaut.server.ssl.trust-name`
- `micronaut.http.client.ssl.key-name` / `micronaut.http.client.ssl.trust-name`

Micronaut ships three provider types:
- File-based: load from files on disk with optional auto-reload
- Resource-based: load from Micronaut resources (classpath:, file:, string:, base64:)
- Self-signed: generate ephemeral certificates (testing/dev)

== File-based provider (PEM with separate key and cert, auto-refresh)

The file provider loads a private key and certificate chain from disk and can automatically reload when files change.

[configuration]
----
micronaut:
  ssl:
    enabled: true
  server:
    ssl:
      # Use the named provider "cert-a" for the server's key/cert
      key-name: cert-a
      key:
        password: ""
  http:
    client:
      ssl:
        # Trust the same material for the client
        trust-name: cert-a

  certificate:
    file:
      cert-a:
        format: pem
        path: /path/to/server.key.pem
        certificate-path: /path/to/server.crt.pem
----

== Resource-based provider (inline PEM and cert-only trust store)

The resource provider loads the material from any Micronaut resource location.

[configuration]
----
micronaut:
  ssl:
    enabled: true
  server:
    ssl:
      key-name: cert-a
  http:
    client:
      ssl:
        trust-name: trust-a
  certificate:
    resource:
      cert-a:
        resource: "string:-----BEGIN PRIVATE KEY-----\n...base64...\n-----END PRIVATE KEY-----\n-----BEGIN CERTIFICATE-----\n...base64...\n-----END CERTIFICATE-----\n"
      trust-a:
        resource: "string:-----BEGIN CERTIFICATE-----\n...base64...\n-----END CERTIFICATE-----\n"
----

For JKS/PKCS12, you can embed binary content via base64:.... For example: resource: "base64:<base64-encoded .p12/.jks bytes>" and set password if required.

== Self-signed provider

The self-signed provider generates temporary certificates. It requires the netty-pkitesting dependency:

dependency:io.netty:netty-pkitesting[scope="runtimeOnly"]

[configuration]
----
micronaut:
  ssl:
    enabled: true
  server:
    ssl:
      key-name: cert-server
      trust-name: cert-client
      client-authentication: need
  http:
    client:
      ssl:
        key-name: cert-client
        trust-name: cert-server

  certificate:
    self-signed:
      cert-server: {}
      # Second provider with a custom subject
      cert-client:
        subject: "CN=foo"
----

For per-listener SSL in Netty server, you can also set `key-name` and `trust-name` under `micronaut.server.netty.listeners.<listener>.ssl`.


== Certificates by server name (SNI)

A Netty TLS listener can serve a different certificate per host name, chosen by the server name the client sends in the TLS handshake (Server Name Indication). Map host names to named certificate providers with `sni-key-names`. The listener's `key-name` (or the global `micronaut.server.ssl.key-name`, or the legacy key store configuration) stays the default certificate for clients that send no server name or one that matches no entry.

[configuration]
----
micronaut:
  ssl:
    enabled: true
  server:
    ssl:
      enabled: true
    netty:
      listeners:
        https:
          port: 8443
          ssl: true
          key-name: default-cert
          sni-key-names:
            "api.example.com": api-cert
            "*.example.org": org-cert
  certificate:
    file:
      default-cert:
        path: /etc/ssl/default.key.pem
        certificate-path: /etc/ssl/default.crt.pem
      api-cert:
        path: /etc/ssl/api.key.pem
        certificate-path: /etc/ssl/api.crt.pem
      org-cert:
        path: /etc/ssl/org.key.pem
        certificate-path: /etc/ssl/org.crt.pem
----

- Host names are matched case-insensitively. An exact entry wins over a wildcard entry; `*.example.org` matches exactly one label (`www.example.org`, but neither `example.org` nor `a.b.example.org`). Internationalized names are matched in their ASCII (punycode) form.
- One SSL context is built per certificate provider and kept up to date the same way as the default one: when a provider publishes a new key store (for example a file provider that watches its files), new connections for its hosts get the new certificate, without affecting the other hosts.
- Protocols, ciphers, ALPN (and so HTTP/2) and `client-authentication` are the same for every host of the listener. Every host trusts the same client certificates as the default certificate: the trust material comes from the listener's `trust-name`, else `micronaut.server.ssl.trust-name`, else the legacy `micronaut.server.ssl.trust-store` when the default certificate comes from the legacy key store, else the JVM default trust store.
- Host specific certificates require named certificate providers; they cannot be combined with a provided `javax.net.ssl.SSLContext` for those hosts.

The TLS server name only selects the certificate: a request is routed by its own `Host`/`:authority`, whatever server name its connection was established with. HTTP/2 clients may also reuse ("coalesce") a connection for another host that the presented certificate covers.

HTTP/3 (QUIC) listeners select the certificate by server name the same way. This includes a legacy or self-signed default certificate.

Routing by host is independent of the certificate selection; see `RequestCondition.host(...)` to restrict routes to a virtual host.
