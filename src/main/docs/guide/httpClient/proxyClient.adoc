A common requirement in Microservice environments is to proxy requests in a Gateway Microservice to other backend Microservices.

The regular api:http.client.HttpClient[] API is designed around simplifying message exchange and is not designed for proxying requests. For this case, use the api:http.client.ProxyHttpClient[], which can be used from an <<filters, HTTP Server Filter>> to proxy requests to backend Microservices.

The following example demonstrates rewriting requests under the URI `/proxy` to the URI `/real` onto the same server (although in a real environment you generally proxy to another server):

snippet::io.micronaut.docs.http.client.proxy.ProxyFilter[tags="imports,class", indent=0, title="Proxy filter that rewrites original requests"]

<1> The filter extends api:http.filter.HttpServerFilter[]
<2> The api:http.client.ProxyHttpClient[] is injected into the constructor.
<3> The `proxy` method proxies the request
<4> The request is mutated to modify the URI and include an additional header
<5> The api:http.uri.UriBuilder[] API rewrites the URI
<6> Additional request and response headers are included

NOTE: The api:http.client.ProxyHttpClient[] API is a low-level API that can be used to build a higher-level abstraction such as an API Gateway.

=== Discarding a Proxied Response

A proxied response holds the body of the upstream response until it is written to the client. A filter that calls `proxy` and then decides not to relay the response, for example because it only accepts a `2xx` response and answers anything else itself, must discard it: a response that is dropped unread leaks what it holds and, on a pooled connection, can keep the connection to the upstream busy.

The `discard` method of api:http.client.ProxyHttpClient[] releases those resources on every runtime. It closes the response bytes, releases a full body in place, drains a streamed body chunk by chunk, and never throws, since the response is being dropped anyway. A response that was already relayed or discarded is left alone.

[source,java]
----
return Flux.from(proxyHttpClient.proxy(upstreamRequest))
    .map(upstream -> {
        if (upstream.status() == HttpStatus.OK) {
            return upstream; // <1>
        }
        proxyHttpClient.discard(upstream); // <2>
        return HttpResponse.status(HttpStatus.BAD_GATEWAY); // <3>
    });
----
<1> The upstream response is relayed as it is.
<2> Any other upstream response is discarded, which releases its body and the connection it was read from.
<3> The filter answers the client itself.

The same method is available on api:http.client.AsyncProxyHttpClient[] for responses obtained through its `CompletionStage` API.

=== Forwarding Headers

To tell the backend who the original client is, write the forwarding headers of the proxied request with api:http.server.util.ForwardedHeaders[]: `X-Forwarded-For`, `X-Forwarded-Proto`, `X-Forwarded-Host`, `X-Forwarded-Port`, `X-Forwarded-Prefix` and the RFC 7239 `Forwarded` header.

[source,java]
----
ForwardedHeaders forwardedHeaders = ForwardedHeaders.builder()
    .trustedProxy(address -> address.getAddress().isSiteLocalAddress()) // <1>
    .build();

forwardedHeaders.write(inboundRequest, proxiedRequest); // <2>
----
<1> Only the forwarding headers sent by a trusted peer are kept. By default no peer is trusted, and the inbound values, which could be forged, are replaced with the values of this hop.
<2> Writes the headers of this hop onto the proxied request.

A trusted proxy is trusted with the values, not with their syntax: an `X-Forwarded-Proto` with a scheme that is not `http`, `https`, `ws` or `wss`, or an `X-Forwarded-Port` with a port that is not a number between 1 and 65535, is dropped, and the value of this hop is sent instead. Such a port is also dropped from an `X-Forwarded-Host`, and such a scheme or port from the `proto` and `host` of a `Forwarded` element. A list of valid values, one per proxy, is kept.
