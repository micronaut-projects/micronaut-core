=== Streaming Clients and Response Types

The example defined in the previous section expects the server to respond with a stream of JSON objects, and the content type to be `application/x-json-stream`. For example:

.A JSON Stream
[source,json]
----
{"title":"The Stand"}
{"title":"The Shining"}
----

The reason for this is simple; a sequence of JSON object is not, in fact, valid JSON and hence the response content type cannot be `application/json`. For the JSON to be valid it would have to return an array:

.A JSON Array
[source,json]
----
[
    {"title":"The Stand"},
    {"title":"The Shining"}
]
----

Micronaut's client does however support streaming of both individual JSON objects via `application/x-json-stream` and also JSON arrays defined with `application/json`.

If the server returns `application/json` and a non-single rs:Publisher[] is returned (such as a Reactor's reactor:Flux[] or a RxJava's rx:Flowable[]), the client streams the array elements as they become available.

The elements are read like the items of a streaming publisher: the events of a `text/event-stream` response (`BodyElements<Event<T>>`, or `BodyElements<T>` for their data), the elements of a JSON stream or a JSON array, or the pieces of any other body (`BodyElements<ByteBuffer<?>>`). Declare `CompletionStage<HttpResponse<BodyElements<T>>>` to read the status and the headers of an event stream or of the pieces of a body as well. A Kotlin `suspend` method that returns `BodyElements<T>` works the same way.

The same is available without a declarative client through the api:http.client.AsyncStreamingHttpClient[], which `toAsync()` returns for a api:http.client.StreamingHttpClient[], and which can be injected with ann:http.client.annotation.Client[]:

snippet::io.micronaut.docs.streaming.AsyncHeadlineClientSpec[tags="async", indent=0, title="AsyncStreamingHttpClient"]

<1> `jsonStream` completes with the elements once the response arrived. `dataStream` and `exchangeStream` read the pieces of the body as they arrive, as heap buffers
<2> `next()` reads one element, `forEach` reads them all, one after the other
<3> Close the elements of a stream that is not read to the end, to release the connection

When the response has an error status, the stage fails with an api:http.client.exceptions.HttpClientResponseException[] whose response carries the error body. The stages complete on an I/O thread: do not block in them.

=== Streaming Clients and Read Timeout

When streaming responses from servers, the underlying HTTP client will not apply the default `readTimeout` setting (which defaults to 10 seconds) of the api:http.client.HttpClientConfiguration[] since the delay between reads for streaming responses may differ from normal reads.

Instead, the `read-idle-timeout` setting (which defaults to 5 minutes) dictates when to close a connection after it becomes idle.

If you stream data from a server that defines a longer delay than 5 minutes between items, you should adjust `readIdleTimeout`. The following configuration in your configuration file (e.g. `application.yml`) demonstrates how:

.Adjusting the readIdleTimeout
[configuration]
----
micronaut:
  http:
    client:
      read-idle-timeout: 10m
----

The above example sets the `readIdleTimeout` to ten minutes.

==== Responses that are either a Single Body or an Event Stream

Some protocols let the server decide, per request, whether to answer with a single body or with an event stream. For example, with the https://modelcontextprotocol.io/specification/2025-11-25/basic/transports#streamable-http[MCP Streamable HTTP transport] the client sends `Accept: application/json, text/event-stream`, and the server answers either with one JSON message or with `text/event-stream`. The client also reads response headers such as `Mcp-Session-Id`.

The `exchangeEventStream` methods of api:http.client.sse.SseClient[] serve these protocols. They emit each event wrapped in an api:http.HttpResponse[] that exposes the status and the headers of the response:

[source,java]
----
MutableHttpRequest<String> request = HttpRequest.POST("/mcp", message)
    .contentType(MediaType.APPLICATION_JSON_TYPE)
    .accept(MediaType.APPLICATION_JSON_TYPE, MediaType.TEXT_EVENT_STREAM_TYPE); // <1>

Flux<String> messages = Flux.from(sseClient.exchangeEventStream(request, Argument.STRING, Argument.STRING)) // <2>
    .doOnNext(response -> response.getHeaders().findFirst("Mcp-Session-Id").ifPresent(sessionId::set)) // <3>
    .mapNotNull(HttpResponse::body) // <4>
    .map(Event::getData);
----

<1> The `Accept` header of the request is kept, since it accepts `text/event-stream`. Otherwise `text/event-stream` is added to it
<2> When the response is `text/event-stream`, each event is emitted as soon as it arrives, and its data is decoded from JSON. Otherwise the whole body is decoded with the content type of the response and emitted as a single event
<3> Each emitted response carries the status and the headers
<4> When the body holds no event, for example for a `202 Accepted` response, a single response without a body is emitted

When the response has an error status, the publisher fails with an api:http.client.exceptions.HttpClientResponseException[] whose response carries the error body, decoded into the given error type, instead of completing empty.

==== Reading Events Asynchronously

The api:http.client.sse.AsyncSseClient[] reads the same responses with a `CompletionStage` instead of a `Publisher`, and without Reactor on the Netty client. Obtain it from an api:http.client.sse.SseClient[] with `toAsyncSse()`, as `toAsync()` returns the api:http.client.AsyncHttpClient[] of an api:http.client.HttpClient[], or inject it with ann:http.client.annotation.Client[]:

snippet::io.micronaut.docs.sse.AsyncSseClientSpec[tags="async", indent=0, title="Async SSE Client"]

<1> The async view shares the client: closing it closes the client
<2> `exchangeEventStream` completes with the response once its status and headers arrived, and fails with an api:http.client.exceptions.HttpClientResponseException[] for an error status. The `Accept` header and the decoding of the body follow the reactive `exchangeEventStream`
<3> The body of the response is a api:http.body.BodyElements[] cursor over the events: the next event is read from the connection when it is asked for. A single body is one event, and a response without a body has no event
<4> `forEach` reads the next event when the stage returned for the previous one completed. `next()` reads one event at a time
<5> The status and the headers of the response are available while the events are read

The connection stays reserved until the events were read to the end or the api:http.body.BodyElements[] was closed, so close the events of a stream that you do not read to the end. The stages complete on an I/O thread: do not block in them. `eventStream` sets `Accept: text/event-stream` and completes with the events only.
