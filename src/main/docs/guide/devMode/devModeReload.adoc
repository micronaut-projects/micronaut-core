A change is handled as one batch: files saved together, across several directories, are compiled and applied together. What the batch does depends on what changed.

== Sources

The changed files are compiled, together with every source whose classes link against a changed or deleted class. An index of which classes reference which finds those sources. They compile with the compile classpath, the annotation processors and the options the build uses.

The class files and generated sources go to a staging directory, and replace the output only when the compilation succeeded. A broken edit therefore leaves the running application as it is:

* the errors are logged;
* when an HTTP server runs, the errors are shown to a browser in place of the page, until the next successful compilation.

== Classes

When a class file changed, the application restarts on a new generation:

. The context of the previous generation is stopped, retaining what a api:context.reload.BeanRetentionPolicy[] asks for.
. A new generation of the class loader is created over a fresh snapshot of the output.
. The application's `main` runs again.

The retained singletons are adopted by the new context under their definitions, so a bean that depends on them is created on top of the same instance.

Two events frame the restart: api:context.reload.ClassChangeEvent[] is published to the old context before it stops, and api:context.reload.ReloadCompletedEvent[] to the new one once it started.

== Method bodies

With `micronaut.dev.strategy=auto` (the default) or `reload`, an edit that changes only method bodies is applied in place, without a restart. An edit qualifies when the structure of every changed class is the same and no generated class changed. The JVM redefines the loaded classes through the agent, and the running beans see the new bodies, in tens of milliseconds.

The agent is `micronaut-dev` itself, launched with `-javaagent`, which the build plugins add. Without it, or with `strategy=restart`, every change restarts.

== Python modules

A Python edit that changes only bodies leaves the classes the compiler generates byte for byte the same: only the module and the bytecode written for it change in the class output. Such a change, in which no class changed and no file was added or removed, is offered to the running context's api:context.reload.InPlaceResourceReloader[] beans before anything restarts.

The Python runtime's reloader patches the edited modules into every GraalPy context of the application: the primary one, the pooled ones and those of the asyncio event loops. In each of them:

* the module, class and function objects stay;
* the functions run the new code;
* the classes get the new members;
* the module's other globals are rebound, except the ones the application injects.

The generation keeps running, under every strategy, `restart` included, since nothing is redefined. `micronaut.dev.patch-in-place=false` turns it off.

What the merge cannot follow is refused, and restarts instead:

* a changed base class or metaclass;
* a function that became a class or a generator;
* a closure over other variables;
* a package initialiser (`__init__.py`) or the main script;
* a module the compiler generated.

Patching is not atomic across contexts: a failure in any of them restarts the application, whose new generation discards what the others applied. Module-level code runs again when a module is patched, so a side effect of it, a registry filled at import, happens again.

== Resources

A changed template, static file or message bundle does not restart anything: it reaches the beans that watch resources of that kind (see the next section).

A changed configuration file is applied in place, without a new generation. The configuration is refreshed: the configuration beans are bound again, the refreshable beans are disposed of, and the configuration watches are told.

The application restarts only when the refresh cannot apply the change:

* a configuration watch answers `REQUIRES_RESTART`;
* a singleton received a changed property through `@Value` or `@Property` rather than a configuration bean;
* a definition's `@Requires` names a changed property, whose presence the change may have flipped.

A bean retained across restarts that watched a changed prefix is not kept when that restart comes.

== Retaining a bean

Two mechanisms say which beans are kept across restarts:

* The manifest's `micronaut.dev.retain` names the types to keep.
* A module can contribute a api:context.reload.BeanRetentionPolicy[] bean instead, which is consulted for every singleton when the context stops, and retains it, refuses it or abstains.

A bean is retained when a policy retains it and none refuses it, whatever their order. A module can therefore refuse what `@Retain` or `micronaut.dev.retain` asks for, such as a client whose configuration names a class of the application that the client instantiates and keeps. A bean that holds a refused bean is not retained either. The refusal is logged at debug under `io.micronaut.context.lifecycle`, naming the policy.

A bean is only retained when its class and everything it received, as the dependency graph records, come from the runtime classpath rather than the reloadable tier. A bean that holds an application class cannot survive a change to that class.

A module declares which of its beans are retained with api:context.annotation.Retain[], on the bean's class or on the factory method that produces it. A module that defines a connection pool does so, so that a restart keeps the pool, and an in-memory database with it.

Set `micronaut.dev.retain-annotated=false` to retain only what `micronaut.dev.retain` names.

Two cases concern pools in particular:

* A pool that a `BeanCreatedEventListener` wraps, as Micronaut Data wraps a data source, is retained as the listener received it, and wrapped again by the new context's listeners.
* A pool is not retained when the factory that made it holds the application context, since destroying the factory would close it. The log says why.

=== When a retained bean is released

A retained bean is dropped and created again when the configuration it was made from changes. That configuration is found from the dependency graph: the prefix of every configuration bean in the retained bean's closure releases it without being named. A configuration bean here is a `@ConfigurationProperties`, an `@EachProperty` entry or another configuration reader, nested configuration included, that one of these received:

* the bean;
* the factory that produced it;
* any singleton it holds.

An `@EachProperty` entry counts under its own prefix, so a change of one entry releases only the beans made from it.

`invalidatedBy` then only names what the bean reads outside configuration beans, such as a raw `@Property` or `@Value`. With an empty `invalidatedBy`, the bean is released by the configuration of its closure alone. The prefixes a policy's `observedConfigurationPrefixes` declares add to it in the same way.

A configuration bean in the closure does not keep the bean from being retained, and is not retained with it. Each generation binds it again, so the retained bean must copy the values it needs rather than keep the configuration bean.

=== HTTP client connections

A restart keeps the idle connections of the Netty HTTP clients, so that the TCP connection, and the TLS handshake of a secure one, are not made again. Each generation still gets its own client objects, codecs, filters and pipeline handlers:

. As a client stops with its generation, it takes its own handlers off each idle HTTP/1.1 connection. What is left is the transport, and the TLS session of a secure connection.
. The next generation's client with the same configuration takes those connections back before its first request, adds its own handlers and pools them.

A connection is kept only when all of these hold:

* It runs on the event loops that are retained across the restart.
* It carries no handler of a `NettyClientCustomizer`, a proxy or a packet capture.
* Its client's configuration, TLS builders and channel factory are not classes of the application.
* Its TLS session comes from the configuration alone, not from certificate providers.
* Its client sets no `connect-ttl`, which a restart would start again, and uses the default connection pool.

HTTP/2 and HTTP/3 connections are not kept: their multiplexing handlers and streams belong to the client that opened them.

A change under `micronaut.http.client`, `micronaut.http.services`, `micronaut.ssl` or the event loops' configuration closes the kept connections. A connection that no client of the next generation takes back is closed when that generation stops.

== What the console shows

The console shows what each reload did: the generation started, the time it took, the classes changed and the beans retained.

Once the new generation serves, the runtime checks that generations older than two are no longer reachable, and warns when one is. A static cache in application code or a thread that was never stopped is the usual cause.
