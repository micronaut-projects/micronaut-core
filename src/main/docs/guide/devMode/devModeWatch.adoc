A bean that derives state from other beans, from configuration or from files registers a watch for the specific things it needs, on api:context.WatchableBeanContext[]. It receives one batch whenever they change.

A watch is described with a fluent request, in the style of the file watcher: the request selects what is watched, and a terminal operation registers the watch. Two rules hold for every watch:

* The state when the watch is registered is the first batch, so a watcher has no separate startup path.
* A watch registered while a bean is being created belongs to that bean, and closes with it.

NOTE: api:context.WatchableBeanContext[] and the types of the `io.micronaut.context.watch` package are public API for modules, marked `@Experimental`. A module that derives state from the context watches it here rather than listening for events, and the API may still change in a minor release. The default context is the only implementation: a module tests for it with `instanceof`, and watches nothing when given another context.

== The requests

* `definitions(Type.class)`, or `definitions()` for every bean, selects bean definitions, narrowed with `qualifier(..)` and `stereotype(..)`:
** Its terminal operations watch the definitions themselves.
** `instances()` continues it as a watch of the beans of those definitions, which it creates.
** `methods(Annotation.class)` continues it as a watch of their executable methods carrying an annotation.
** `@EachProperty` and `@EachBean` beans are selected one per entry, as the context resolves them.
* `methods(Annotation.class)` watches the executable methods of every bean carrying an annotation: the reload-aware form of an `ExecutableMethodProcessor`.
* `configuration(prefix)` watches a configuration prefix, and `configuration()` every change.
* `resources(ResourceKind.VIEWS).include("**/*.html")` watches the files of a resource kind, by glob.
* `classChanges()` watches the class changes of a reload.

A definition or method that comes back in a new generation is paired with the one it replaces, and the pair says whether only bodies changed.

== Batches and per-change handlers

The batch is the unit of delivery. A reload retires one generation's definitions and adds the next one's in a single batch, so a watcher that aggregates what it selects, like the route table above, never sees a half-applied reload.

A watcher that handles one change at a time adds per-change handlers to the request instead. They are called for each change once its batch is applied:

* `onAdded`;
* `onRemoved`;
* `onReplaced`, for a new generation of the same bean or method, which is otherwise a removal followed by an addition.

== Watching configuration

A configuration watcher runs after the configuration beans under its prefix were bound again. There are two kinds:

* A plain `ConfigurationWatcher`, registered with `watch(..)`, applies the change.
* A watcher that cannot always apply it is a `ReloadingConfigurationWatcher`, registered with `watchReloading(..)`. It says what it did:
** `APPLIED` when it changed the live bean;
** `RECREATE` when the bean that registered the watch must be replaced, in which case the context replaces it and the beans that received it;
** `REQUIRES_RESTART` when nothing short of a restart applies the change;
** `IGNORED`.

A configuration watch has no first batch unless it asks for one. `configuration(prefix).withFirstBatch()` calls the watcher once with a change whose `initial()` holds, so that the bean reads its configuration inside the watch. As every first batch is, the call is delivered at once when the context is running, or when it starts for a watch registered before. What a reloading watcher answers to that call is not acted on.

== The first batch and the order of changes

A bean that reads the definitions or configuration it derives state from, and only then registers a watch, can miss a change made in between. The first batch closes that gap: it is read after the watch is registered, so a bean that builds its state from the first batch, instead of from a read of its own, misses nothing.

* Batches reach a watcher one at a time, the first batch first, then the changes in the order they were made. No change is delivered before the first batch or alongside another, and no lock is held while a watcher runs.
* A change applied before the first batch began to be read shows in it, and is not delivered again. One applied after it was read is delivered after it.
* Only a change applied while the first batch was being read can show in it and be delivered after it too. A watcher therefore treats an addition it already has, or a removal of something it never had, as nothing to do.

== Class changes

A cache keyed by class is not a set of beans: it forgets what a reload retires. `classChanges()` gives the watcher every api:context.reload.ClassChangeEvent[] the launcher publishes, ahead of the listeners of the event, with the same ownership as the other watches.

Classes only change in development mode. Outside it the watch registers nothing and is returned inactive, so the module needs no listener bean gated on development mode.

== Recreating a bean

When a change cannot be applied to a bean in place, the watcher asks the context to recreate it, with `recreate(bean)`, or `recreate(Type.class, qualifier)` for the singleton of a type. Recreating a bean:

. destroys the beans that received it, as the dependency graph records them;
. destroys the bean and creates it again;
. creates the dependents again when next requested, on top of the new instance. An `ExecutableMethodProcessor` among them is created again at once, and given the methods it was given at startup.

This is more than destroying the bean and getting it again, which would leave its dependents holding the destroyed instance.

Both methods return whether anything was recreated, which a prototype, a bean of a custom scope or a singleton registered at runtime never is.

They are meant for development-time watches. The dependents are known only when the context tracks bean dependencies, which by default only a context in development mode does; `ApplicationContextBuilder.beanDependencyTrackingEnabled(true)` turns it on elsewhere. A context that does not track them recreates nothing and returns false.

== Resources

Resources are watched the same way: a template engine registers `resources(ResourceKind.VIEWS).include("**/*.html").watch(change -> ...)` and clears what the change affects, rather than filtering an event every engine receives.

NOTE: Existing api:context.processor.ExecutableMethodProcessor[] and api:context.processor.BeanDefinitionProcessor[] beans keep working. The context feeds them what is added after startup, through an adapter that sees additions only, which is also how the launcher tells that such a processor cannot follow a reload.
