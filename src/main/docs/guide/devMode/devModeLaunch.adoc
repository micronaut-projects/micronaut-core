== The manifest

The launcher reads a manifest, a `java.util.Properties` file the build tool writes. The manifest names:

* the main class;
* the directories holding the compiled classes and resources, which form the reloadable tier;
* the compile and annotation processor classpaths;
* the source directories, by language;
* the resource directories, by kind.

[source,properties]
----
micronaut.dev.main-class=example.Application
micronaut.dev.reloadable=build/classes/java/main,build/resources/main
micronaut.dev.compile-classpath=@build/micronaut-dev/compile.argfile
micronaut.dev.processor-path=@build/micronaut-dev/processors.argfile
micronaut.dev.sources.java=src/main/java
micronaut.dev.resources.config=src/main/resources
micronaut.dev.resources.views=src/main/resources/views
micronaut.dev.resources.static=src/main/resources/static
micronaut.dev.compile.java.output=build/classes/java/main
micronaut.dev.retain=javax.sql.DataSource
micronaut.dev.patch-in-place=true
----

The launcher reads the entries as follows:

* Relative paths resolve against the manifest's directory.
* `@file` reads a list from an argument file.
* A system property of the same name overrides an entry.

On macOS, put `micronaut-runtime-osx` on the development runtime classpath as well, which the build plugins do. The launcher then watches through the native file system events, and a save is noticed at once.

Without it, and in a native image, the launcher compares the watched directories every 250 milliseconds, rather than use the JDK's service, which polls every two seconds at best.

The launcher snapshots the reloadable tier for each generation into `build/micronaut-dev/generations` under the project, or the directory `micronaut.dev.generations` names, such as a Maven build's `target/micronaut-dev/generations`. It empties that directory when it starts, and refuses to when it holds files it did not write.

== Starting the launcher

The launcher is started with the runtime classpath, which holds the framework, the libraries and `micronaut-dev` itself. It does not hold the project's own class directories: those belong to the reloadable tier.

[source,bash]
----
java -cp @build/micronaut-dev/runtime.argfile io.micronaut.dev.MicronautDevMain --manifest build/micronaut-dev/dev.properties
----

The launcher compiles every language whose class output does not exist yet, so it works from a clean checkout. It then runs the application's own `main` on a thread of its own.

The application does what it always does, `Micronaut.run(Application.class, args)`. An `ApplicationContextConfigurer` the module ships gives the context:

* the reloadable loader;
* the `dev` environment;
* `micronaut.dev.enabled=true`;
* the beans retained from the previous generation.

TIP: Everything under the manifest's `micronaut.dev.` keys can be set as a system property. api:context.env.DevelopmentMode[] answers whether the application runs this way, so a bean can be conditioned on it with `@DevelopmentActive` (or `@DevelopmentInactive` for the opposite).

== The dev endpoint

With `micronaut-management` on the classpath, the application has a `dev` endpoint:

* `GET /dev` reports the generation, the reload strategy, the watched roots and the last compilation failure.
* `POST /dev/reload` compiles everything and restarts if anything changed. It is the way to recover when the watcher missed an edit, and the gate that answers requests with a compilation failure lets it through.

The endpoint moves with `endpoints.all.path` and `endpoints.dev.path`, like any other.

The endpoint is sensitive: its status holds absolute paths of the machine, and its reload compiles and restarts the application. It therefore answers 401 until Micronaut Security protects it, or until a development configuration opts out:

[configuration]
----
endpoints:
  dev:
    sensitive: false
----

The reload is a JSON request. It is refused with a 403 when a browser marks it as coming from another site, or when its `Origin` is not the server's own as its host resolution gives it (behind a proxy, from the forwarding headers). A page the developer visits therefore cannot trigger it with a form:

[source,bash]
----
curl -X POST -H 'Content-Type: application/json' http://localhost:8080/dev/reload
----

== Compilers

The launcher compiles each language with a compiler of its own, all of them incrementally. The changed sources and every source whose classes reference them are compiled together against the previous output, and the outputs replace the old ones only when the compilation succeeded.

* Java compiles through the JDK's own `javac`, with the annotation processors of the processor path.
* Groovy compiles through the project's own Groovy on the launch classpath, with the Micronaut AST transformations the compile classpath carries.
* Kotlin compiles through the Kotlin Build Tools API when `kotlin-build-tools-impl` is on the launch classpath at the project's Kotlin version. It runs the symbol processors of the processor path first when `symbol-processing-aa-embeddable` is there at the project's KSP version. The `-A` options of the language pass to the processors, and the other options to `kotlinc`.

The build plugins put these artifacts on the launch classpath for the languages the project uses, so `micronaut-dev` itself depends on neither Kotlin nor Groovy.

Python compiles through the Pyronaut compiler of `micronaut-inject-python` when it is on the launch classpath:

* The compiler generates the Java stubs and bean definitions of the Python modules, and compiles them in one `javac` run with the module's Java sources, since each references the other. When the Java sources share the Python class output, the Python compiler compiles them too, with the options of both languages, and `javac` never runs on them alone.
* The compiler plans its incremental work itself and keeps its state beside the class output. In one transaction, it then copies what changed into the class output and the generated stubs into the generated sources directory, and removes what it no longer produces.

The Python modules are resources of the class output, so a Python edit starts a new generation, whose GraalPy context imports the new modules; the GraalPy engine stays loaded.

The native image of Pyronaut runs the launcher too. The image is the parent tier, and each generation's classes are defined at runtime by GraalVM's runtime class loading (`-H:+RuntimeClassLoading`), with the framework methods they call kept in the image by `-H:Preserve`. In a native image:

* a body-only edit restarts the generation, since a native image cannot redefine a class;
* on macOS, the FSEvents watch service of `micronaut-runtime-osx` cannot be loaded, since it uses JNA, so the image compares the watched directories every 250 milliseconds instead.

== Generation budget

On the JVM, a retired generation is unloaded once nothing refers to its classes. In a native image it never is: the classes GraalVM defines at runtime stay for the life of the process, in a metaspace whose size is fixed when the image is built, with the interpreter's data on the heap.

The launcher therefore counts generations against a budget, `micronaut.dev.max-generations`. When a change would start one generation more:

. the change is compiled;
. the runtime closes;
. the launcher exits with status `3` (`MicronautDevMain.RELAUNCH`);
. whoever started it starts it again, and the new process starts from the classes that change compiled.

The budget is unlimited on the JVM, and 50 generations in a native image (`DevManifest.NATIVE_MAX_GENERATIONS`). The native budget was measured on a Pyronaut application, where a retired generation leaves only its classes and their data behind, about 1.3 MB of heap each, and 61 generations stayed under 1 GB of resident memory.

`unlimited` or `0` lifts the budget. In test mode a run beyond it ends the same way, with `runForStatus` returning the status.

== LiveReload

Add `micronaut-dev-livereload` to the development runtime classpath and the launcher starts a LiveReload server on port 35729 (`micronaut.dev.livereload.port`). Adding the module is the switch: there is no other setting to turn it on. Browsers then:

* reload when the application restarted or a template changed;
* swap a stylesheet in place when only a stylesheet changed.

Pages get the client script appended before their closing body tag; set `micronaut.dev.livereload.inject-script=false` if you use a browser extension. A api:dev.livereload.LiveReloadTrigger[] bean lets a module ask for a refresh.

The server listens on the loopback address only, and its socket accepts the clients LiveReload is made for:

* native clients, which send no `Origin`;
* the browser extensions (`chrome-extension:`, `moz-extension:` and `safari-web-extension:` origins);
* pages served by `localhost`, a `*.localhost` name or the loopback address, on any port;
* pages of the origins listed in `micronaut.dev.livereload.allowed-origins`, none by default.

A page of any other site is refused, so that a site the developer visits cannot follow the reloads. This holds for the script a browser extension injects too, since it runs in the page and connects with the page's origin. Open the application through `localhost`, the loopback address or a name under `.localhost`, such as `myapp.localhost`, which browsers resolve to the loopback address.

When the browser opens the application through another name, such as a LAN host or the name of a development container whose ports are forwarded, list that name in `micronaut.dev.livereload.allowed-origins`, comma-separated, in the manifest or as a system property of the launcher:

[source,properties]
----
micronaut.dev.livereload.allowed-origins=http://devbox.lan:8080,app-container
----

An origin, `http://devbox.lan:8080`, allows pages of that scheme, host and port, the default port matching an origin that leaves it out; a host name alone, `app-container`, allows its pages over HTTP or HTTPS on any port. The loopback origins and the extensions stay allowed. No pattern is accepted: an entry with a `*`, or one that is neither an origin nor a host name, is ignored with a warning, so the socket never opens to every site. The setting only decides which pages may connect: the server still listens on the loopback address, so the LiveReload port must reach it from the browser, as forwarded ports or an SSH tunnel do. The event channel and the pages the server serves stay those of `localhost`.

=== Serving other pages

The server also serves pages that are not the application's, such as a test report:

* `LiveReloadServer.serve(prefix, directory)` mounts a directory at an `http://localhost:35729` address, with the client script in its HTML. Nothing outside the directory is served.
* A page that follows something as it happens subscribes to a topic of the event channel, `ws://localhost:35729/micronaut-dev/events?topic=<topic>`, and receives the JSON that `LiveReloadServer.publish(topic, json)` sends. The channel is apart from the LiveReload socket, whose clients reject commands they do not know.

A component reaches the server through `DevRuntime.current().liveReload()`, in test mode too.
