The launcher reads a manifest, a `java.util.Properties` file the build tool writes, that names the main class, the directories holding the compiled classes and resources (the reloadable tier), the compile and annotation processor classpaths, the source directories by language, and the resource directories by kind:

[source,properties]
----
micronaut.dev.main-class=example.Application
micronaut.dev.reloadable=build/classes/java/main,build/resources/main
micronaut.dev.compile-classpath=@build/micronaut-dev/compile.argfile
micronaut.dev.processor-path=@build/micronaut-dev/processors.argfile
micronaut.dev.sources.java=src/main/java
micronaut.dev.resources.config=src/main/resources
micronaut.dev.resources.views=src/main/resources/views
micronaut.dev.resources.static=src/main/resources/static
micronaut.dev.compile.java.output=build/classes/java/main
micronaut.dev.retain=javax.sql.DataSource
----

On macOS, put `micronaut-runtime-osx` on the development runtime classpath as well, which the build plugins do: the launcher then watches through the native file system events instead of the JDK's polling service, and a save is noticed at once rather than seconds later.

Relative paths resolve against the manifest's directory, `@file` reads a list from an argument file, and a system property of the same name overrides an entry. The launcher is started with the runtime classpath, which holds the framework, the libraries and `micronaut-dev` itself, but not the project's own class directories: those belong to the reloadable tier.

[source,bash]
----
java -cp @build/micronaut-dev/runtime.argfile io.micronaut.dev.MicronautDevMain --manifest build/micronaut-dev/dev.properties
----

The launcher compiles every language whose class output does not exist yet, so it works from a clean checkout, then runs the application's own `main` on a thread of its own. The application does what it always does, `Micronaut.run(Application.class, args)`; an `ApplicationContextConfigurer` the module ships gives the context the reloadable loader, the `dev` environment, `micronaut.dev.enabled=true`, and the beans retained from the previous generation.

TIP: Everything under the manifest's `micronaut.dev.` keys can be set as a system property, and api:context.env.DevelopmentMode[] answers whether the application runs this way, so a bean can be conditioned on it with `@Requires(condition = DevelopmentMode.Active.class)`.

=== Compilers

The launcher compiles each language with a compiler of its own, all of them incrementally: the changed sources and every source whose classes reference them are compiled together against the previous output, and the outputs replace the old ones only when the compilation succeeded. Java compiles through the JDK's own `javac` with the annotation processors of the processor path. Groovy compiles through the project's own Groovy on the launch classpath, with the Micronaut AST transformations the compile classpath carries. Kotlin compiles through the Kotlin Build Tools API when `kotlin-build-tools-impl` is on the launch classpath at the project's Kotlin version, and runs the symbol processors of the processor path first when `symbol-processing-aa-embeddable` is there at the project's KSP version; the `-A` options of the language pass to the processors, and the other options to `kotlinc`. The build plugins put these artifacts on the launch classpath for the languages the project uses, so `micronaut-dev` itself depends on neither Kotlin nor Groovy.

Python compiles through the Pyronaut compiler of `micronaut-inject-python` when it is on the launch classpath. The compiler generates the Java stubs and bean definitions of the Python modules and compiles them in one `javac` run with the module's Java sources, since each references the other: when the Java sources share the Python class output, the Python compiler compiles them too, with the options of both languages, and `javac` never runs on them alone. The compiler plans its incremental work itself and keeps its state beside the class output, then copies what changed into the class output, the generated stubs into the generated sources directory, and removes what it no longer produces, all in one transaction. The Python modules are resources of the class output, so a Python edit starts a new generation, whose GraalPy context imports the new modules; the GraalPy engine stays loaded. Reloading needs a JVM: a native image can neither define the classes of a new generation nor redefine a class, so the native toolchain of Pyronaut restarts the process instead.

=== LiveReload

Add `micronaut-dev-livereload` to the development runtime classpath and the launcher starts a LiveReload server on port 35729 (`micronaut.dev.livereload.port`): browsers reload when the application restarted or a template changed, and swap a stylesheet in place when only a stylesheet changed. Pages get the client script appended before their closing body tag (`micronaut.dev.livereload.inject-script=false` for users of a browser extension), and a api:dev.livereload.LiveReloadTrigger[] bean lets a module ask for a refresh. Adding the module is the switch: there is no other setting to turn it on.
