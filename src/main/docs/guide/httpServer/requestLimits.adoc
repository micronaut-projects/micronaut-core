The server can shed load before it reaches your code: request limiters reject requests over a rate or over a number of requests in flight, and the Netty server can cap its open connections. Nothing is limited unless you configure it.

=== Request Limiters

A request limiter is configured under `micronaut.server.limits.<name>`. Two kinds are built in:

* `concurrency` (api:http.server.limit.ConcurrencyRequestLimiter[]): at most `max-concurrent` requests in flight. A request is in flight from the moment the limiter grants it until its response is written, fails, or the client goes away. A request over the limit is rejected with `503 Service Unavailable`, with a `Retry-After` header only if you configure a `retry-after` hint.
* `rate` (api:http.server.limit.RateRequestLimiter[]): a token bucket that allows `permits` requests per `period`, refilled evenly, with up to `burst` requests at once (default: `permits`). A request that finds the bucket empty is rejected with `429 Too Many Requests` and a `Retry-After` header with the seconds until the next token, rounded up.

A limiter applies to the paths that match its `patterns`, in the Ant style:

[configuration]
----
micronaut:
  server:
    limits:
      api:
        type: rate
        permits: 100
        period: 1s
        burst: 20
        patterns:
          - /api/**
      reports:
        type: concurrency
        max-concurrent: 8
        retry-after: 5s
----

A limiter without patterns applies only to the routes that select it by name. Select it on a controller or a method with ann:http.server.limit.RequestLimit[]:

<1> The `reports` limiter applies to this route, in addition to the limiters whose patterns match its path.

A functional route selects limiters with the `RequestLimit.ATTRIBUTE` attribute, a name or a list of names:

snippet::io.micronaut.docs.server.limit.LimitedReportRoutes[tags="imports,clazz", indent=0, title="A limiter selected by a functional route"]

<1> The attribute names the `reports` limiter.

A route that names a limiter that is not configured fails the startup of the application, also when no limiter is configured at all, so that it never runs uncapped by mistake. A route that a route locator finds later is checked when it is matched.

A request goes through every limiter that applies to it, the pattern limiters first; if one rejects it, or fails, the permits it took from the others are given back.

The limiters run in a server filter just after the CORS filter, so that a rejection still carries the CORS headers. The rejection is a api:http.server.limit.RequestLimitExceededException[], handled like any other error by api:http.server.limit.RequestLimitExceededExceptionHandler[]: replace that handler, or add an <<errorHandling, error route>>, to answer differently. The exception carries no stack trace.

=== Custom Limiters

Any bean of type api:http.server.limit.RequestLimiter[] can be selected by its name. `tryAcquire` receives the request, so an implementation can partition its permits, for example by the client address. It must not block: it runs on the event loop. Return `Acquisition.granted(release)` with the action that gives the permit back, which runs once, or `Acquisition.rejected(status, retryAfter)`.

The server gives a permit back once the response is done, see `ServerHttpRequest.whenResponseCompleted`. A server that cannot tell gives it back when the response leaves the filters.

=== Reading the State of a Limiter

A api:http.server.limit.RequestLimiter[] is also a api:http.limit.LimiterState[]: its permits in flight and available, and the counts of granted and rejected requests. A metrics module reads them from the limiter beans, e.g. as gauges named after `getName()`.

=== Limiting Connections

The Netty server closes the TCP connections over `micronaut.server.netty.max-connections` as soon as it accepts them. The limit counts the connections of all listeners together; HTTP/3 connections are not counted. The default, `0`, means no limit.

[configuration]
----
micronaut:
  server:
    netty:
      max-connections: 10000
----
