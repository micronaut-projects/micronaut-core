Choose the filter scope according to the requests it should cover:

* *Route filters* apply to one matched route: `routes.GET(uri).before(...).and().handle(...)`.
* *Group filters* apply to matched routes in a group and its nested groups.
* *Server filters*, declared with `routes.serverFilter(patterns...)`, apply to all matching request paths, including controller routes, static resources and unmatched requests.

Use a server filter when you need to cover responses such as `404`, `405`, `415` or `406` that occur before a route is selected. Only the top-level builder declares server filters.

=== Filter Methods

[cols="1,2"]
|===
|Method |Behaviour

|`before(...)`
|Change the request in place and continue.

|`beforeReplacing(...)`
|Return a response to stop processing, a replacement request to continue, or `null` to keep the current request.

|`after(...)`
|Change the response in place.

|`afterReplacing(...)`
|Return a replacement response, or `null` to keep the current response.
|===

Each method has an asynchronous variant, such as `beforeAsync` or `afterReplacingAsync`, that returns a `CompletionStage`. The chain continues when that stage completes.

Overloads can receive api:core.propagation.MutablePropagatedContext[], for example `before((request, context) -> ...)`. Added context is available to subsequent filters, the handler and error routes. Asynchronous context changes take effect when the stage completes.

=== Changing Requests and Responses

Use `before` for in-place changes to headers, attributes or the URI. Use `beforeReplacing` to supply a replacement request, including one with a different method or body. Replacing the raw body requires a `ServerHttpRequest` with the replacement `byteBody()`.

Only a *pre-matching server filter* can change which route is selected. A later URI or method change does not trigger routing again.

Use `after` to update response headers or other mutable properties, and `afterReplacing` to return an entirely different response.

=== Filter Order

Request processing proceeds through:

. Server filters, including `@ServerFilter` beans, sorted together by order. Pre-matching filters run before routing.
. Outer group filters, then nested group filters.
. Route filters.
. The handler.

Responses pass back through the scopes in reverse order. Within each route or group, request filters and response filters each retain declaration order. Response filters also see responses returned early by request filters at their own or an inner scope.

Filter failures use the normal error routes and exception handlers.
