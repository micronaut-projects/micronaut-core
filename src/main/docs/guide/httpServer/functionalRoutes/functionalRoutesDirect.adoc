An api:web.router.builder.HttpDirectRoutes[] bean declares *direct routes*: the server answers a request the route matches as soon as it has received it, from its method, path, headers and peer address, before it creates the api:http.HttpRequest[], runs the filters and looks up the ordinary routes. A direct route is the cheapest answer the server can give, for liveness and readiness probes, static answers such as `robots.txt`, and answers that read only the headers of the request, such as a conditional `GET`.

WARNING: *No filter runs for a direct route*, of any kind: no `@ServerFilter` or api:http.filter.HttpServerFilter[] bean, no server filter of an `HttpRoutes` bean, no filter of a group, and so none of the filters of Micronaut Security, CORS or the session. A direct route must never answer with protected content. Declare a <<functionalRoutesRespond, `respond(...)` route>> instead, which the filters see.

`HttpDirectRoutes` is a sibling of `HttpRoutes`, with its own builder, api:web.router.builder.DirectRouteBuilder[]: a direct route shares nothing with the ordinary routes, so it cannot be declared in a group of ordinary routes and inherit its filters, its port or its executor by accident. The builder has the methods of a direct route only, and a path prefix. The beans declare their routes when the application starts, under `micronaut.server.context-path`, and their order only orders the beans, like the order of the `HttpRoutes` beans.

snippet::io.micronaut.docs.server.functional.DirectRoutes[tags="imports,clazz", indent=0, title="Direct routes"]

<1> `path(...)` declares routes under a path prefix, like `path(...)` of `HttpRouteBuilder`: the prefix is all they share.
<2> A shortcut: a response given as a value, the same as `GET(uri).respond(response)`. The route copies its status and headers for each request, and shares only its body, a text encoded once.
<3> The terminal `respond(Function)` ends the pending route with a function that composes the response of each request from a api:web.router.builder.DirectContext[]: `request()`, the request as the server received it, and `pathVariables()`, the path variables of the route. The constraints of the route select the values it answers: another value continues to the ordinary routes.
<4> A static answer with its own content type.
<5> A conditional `GET`: the function reads the `If-None-Match` header of the request with `request()`, and answers `304` when the client has the current version.
<6> `route(Set<HttpMethod>, uri)` declares the route for several methods, here `GET`, and so `HEAD`, `POST`, `PUT`, `PATCH` and `DELETE`, on any path: `/{+path}` is the least specific template.
<7> A block list: the requests of those methods whose `User-Agent` names a bad bot, or that come from an address range, are answered with `403` before any filter or ordinary route runs for them. The more specific direct routes, such as `/probe/live` or `/robots.txt`, still answer them: a direct route ranks by its URI template first, see <<functionalRoutesDirectMatching, Matching>>.

A direct route is declared in stages, like an ordinary route: a creator of the builder, `GET(uri)`, `POST(uri)`, `PUT(uri)`, `PATCH(uri)`, `DELETE(uri)`, `HEAD(uri)` or `OPTIONS(uri)`, `route(HttpMethod, uri)` for a method given as a value, or `route(Set<HttpMethod>, uri)` for several methods, returns the pending route, a api:web.router.builder.DirectRouteSpec[]; its settings come next; one terminal ends it: `respond(HttpResponse)` with a response given as a value, `respond(Function<DirectContext, HttpResponse>)` with a function, or `respondAsync(...)` with a function that completes the response later. A route with no settings that answers with a value has a shortcut per method, e.g. `GET(uri, HttpResponse)`: unlike the shortcut `GET(uri, handler)` of an `HttpRoutes` bean, it takes the response, not a function. A pending route without a terminal fails the startup, with a message that names it and its `HttpDirectRoutes` bean.

WARNING: An `OPTIONS(uri)` direct route also answers the CORS preflight requests of its paths, as no filter runs for it, the CORS filter neither: without the CORS headers, a browser rejects the cross-origin requests it covers. A route that leaves them to the CORS filter excludes them with a condition, e.g. `where(RouteCondition.not(RouteCondition.header(HttpHeaders.ACCESS_CONTROL_REQUEST_METHOD)))`.

The function creates its response with the static methods of `HttpResponse`, e.g. `HttpResponse.ok(...)`, which create the response type of the server runtime: the server writes it as it is, without converting it. A response of another type, e.g. one a library returns, still works: the server converts it. The function reads the request with `request()`, a api:web.router.direct.DirectRequest[]: its method, its path, its headers, its query parameters and the address of its peer, each read when the function asks for it. A route of several methods reads the method of the request there, as does a `GET` route that answers a `HEAD` request. A function that reads a query that is not valid declines the request, which the server answers with `400` on its ordinary path. To test a function without a server, `DirectContext.of(request, pathVariables)` creates its context.

The settings of a `DirectRouteSpec` are `where(...)`, `constrain(...)`, with the overloads of an ordinary route, e.g. `constrain("id", Long.class, id -> id > 0)`, see api:web.router.builder.MatchSpec[], `order(...)`, and the `executeOn(...)` and `nonBlocking()` of <<functionalRoutesDirectAsync, executors>>, and nothing else: a direct route has no filters, media types, annotations, attributes, error routes or port.

=== How a direct route answers

The server looks up the direct routes for every request it receives, before it creates the request: nothing else runs for a request a direct route matches. A request the server could not decode, e.g. with a malformed header or headers longer than the server allows, or whose target is not a valid URI, e.g. with a malformed percent escape, is never looked up: it is answered with `400` or `413`, as usual. There is no api:http.HttpRequest[], so there are no request events, no request scope, no propagated context and no `ServerRequestContext`; the error routes and the status routes do not apply; the body of the request is discarded without being read once the route answers.

The server writes exactly the status, the headers and the body of the response, composed for each request, and adds only what the protocol needs to frame it, the `Content-Length` of the body and the handling of the connection, keep-alive or close, and the headers it is configured to add to every response: the `Date` header, formatted at most once per second, unless `micronaut.server.date-header` is `false`, and the `Server` header of `micronaut.server.server-header`, if set. A `Date` or `Server` header the route sets replaces the server's. *A direct response gets no other header from the server*: no `Content-Type`, and none of the headers of a filter. Another server runtime may add a header it cannot leave out, see <<functionalRoutesDirectRuntimes, the other runtimes>>. The compression of the connection, which a client asks for with `Accept-Encoding`, applies to a direct response as to any other: it is part of the transfer, with its `Content-Encoding`.

The body is written as it is when it is bytes or text: a `byte[]` or a `java.nio.ByteBuffer`, wrapped without a copy and never changed, so one array may serve every response, a Netty `ByteBuf`, written once and released, e.g. `shared.retainedDuplicate()` returned for each request, or a `CharSequence`, encoded with the charset of its content type, UTF-8 without one. Any other body, e.g. a record, is written for each request by the message body writer of its content type, `application/json` if the response has none, which it then gets, like the body of an ordinary route; the writer is looked up once per body type. A function that throws, or a body that cannot be written, is answered with `500`. A status that has no body, `1xx`, `204` or `304`, is written without the body of the response and without a `Content-Length`, whatever the route set.

The function of a route is called on the event loop that received the request, unless the route is asynchronous, and the body of its response is written there: it must be fast and must not block, like the constraints. A message body writer that blocks, an api:http.body.MessageBodyWriter[] whose `isBlocking()` is `true`, is refused on such a route, and the request answered with `500`. *Blocking work belongs on an executor or in an asynchronous route*, see <<functionalRoutesDirectAsync, below>>.

A response given as a value is copied for each request, with the response factory of the server: its status, headers and attributes, so that nothing is shared but its body, which the requests share. A text body is encoded once, when the route is declared, and a `byte[]` body is copied then. A body that is consumed when it is written, such as a Netty `ByteBuf`, which the server releases, is copied to bytes once, when the route is declared, and released.

A `GET` direct route also answers `HEAD` requests, with the headers of its response, its `Content-Length` included, and no body, unless a `HEAD` direct route matches them as well or better, see <<functionalRoutesDirectMatching, Matching>>. A `HEAD` direct route without a body may declare the `Content-Length` of the `GET` response itself, which the server keeps; a status without a body, such as `204`, has none. A `HEAD` direct route that declines a request, synchronous or asynchronous, hands it to the ordinary routes, not to the `GET` direct route of the path. The response is written like any other response of the server, in the order of the requests of the connection, so keep-alive and HTTP/1.1 pipelining work across direct and ordinary routes. Over HTTP/2, and HTTP/3, the server converts each stream to a request before it looks up the direct routes, so a direct route answers the streams of a connection the same way.

[[functionalRoutesDirectAsync]]
=== Executors and asynchronous routes

A direct route runs on the thread that received the request, whatever the thread selection of the server: `nonBlocking()` is its default, and it inherits no executor from anywhere. `executeOn(name)` runs it on the named executor, like `@ExecuteOn`: the route is still matched on the thread that received the request, by its URI template, its conditions and its constraints, then the server holds the request while the function composes the response on the executor. A function that returns a `CompletionStage` of the response ends the route with the terminal `respondAsync(...)`: it is called on the thread that received the request, or on the executor of the route, and the stage may complete on any thread. A route that answers with a response given as a value has nothing to run on an executor: `executeOn(...)` before `respond(HttpResponse)` fails the startup.

snippet::io.micronaut.docs.server.functional.AsyncDirectRoutes[tags="imports,clazz", indent=0, title="A route on an executor, and an asynchronous route"]

<1> The function blocks, e.g. on a database: it may, as it runs on an executor. `null` declines the request, as for any direct route.
<2> `executeOn(...)` runs the function on the named executor, here `TaskExecutors.BLOCKING`.
<3> An asynchronous route returns the stage of its response, e.g. the response of a non-blocking client, and does not block the thread that received the request.
<4> A stage completed with `null` declines the request: it continues to the ordinary routes, with its body untouched.

An asynchronous route, on an executor or completed later, answers like any direct route: without a filter or a request, with the headers of its response only, in the order of the requests of the connection, so a response completed after the response of a later request is still written first under HTTP/1.1 pipelining, and over HTTP/2 the same way. Until the stage completes, the server holds the request, and neither reads nor discards its body: a declined request reaches the ordinary routes as if no direct route had matched it. The server cancels the stage when the request is abandoned: the connection closes, or, over HTTP/2, the client resets the stream of the request. It releases the body of a response the route completes after that, e.g. a buffer, as it never writes it. It answers a failed stage, or a function that throws, with `500`.

The body of the response of an asynchronous route may be written by a blocking message body writer: on the executor of the route, or, when the stage completes on an event loop, on the IO executor of the server. An executor that does not exist fails the startup with a message that names it and the route.

[[functionalRoutesDirectMatching]]
=== Matching

The URI template of a direct route, under its prefix and the context path, is matched like the URI template of an ordinary route, and the direct routes rank among themselves like the router ranks its routes: the most specific template first, then the constraints and the conditions, then the lowest order. A `HEAD` request is matched against the `HEAD` direct routes and the `GET` direct routes together, and an explicit `HEAD` route wins over a `GET` route only when they are equally specific, whatever their order, as in the router. Direct routes of the same specificity and order that both match a request make it ambiguous, answered with `400`. Two routes of the same method, URI template and order, without a condition or a constraint, would make every request they match ambiguous: they fail the startup, with a message that names both.

The order only breaks ties between equally specific routes: a guard route on a catch-all template, like the block list above, never comes before a more specific direct route. A route that the guard must cover too takes the guard's condition itself, e.g. `where(RouteCondition.not(blocked))`.

A direct route is not a route of the router. It answers the requests it matches before any ordinary route, whatever their specificity: a direct route `/{+path}` answers every request its conditions accept, even one to a more specific controller route.

NOTE: A direct route answers before any ordinary route on the same path, e.g. a controller route or a handler route with the same URI template: the ordinary route only sees the requests the direct route does not answer.

A request that no direct route matches, because of its path, method, conditions or constraints, continues as usual, to the filters and the ordinary routes, which may answer it with a `404` or a `405`.

A function that returns `null` declines the request: the server handles it as if no direct route matched it, before the body of the request is read or discarded. An ordinary route on the same path answers it, and can read its body, or it is answered with `404` as usual. A direct route can so answer the common case cheaply and leave the rest to an ordinary route:

=== Conditions

A direct route takes the conditions the server decides from the request it received:

* `RouteCondition.method(...)`;
* `RouteCondition.header(...)` and `RouteCondition.cookie(...)`, read from the headers as they were received;
* `RouteCondition.query(...)`, decoded from the URI like the parameters of an ordinary request, with the charset of the content type of the request or the default charset of the server and its limits. The query is decoded only when a route with a query condition is tried, once per request;
* `RouteCondition.host(...)`, which reads the `Host` header, or the authority of an HTTP/2 request, and never a forwarded header or the host resolver of the server;
* `RouteCondition.peerAddress(...)`, the address of the peer of the connection;
* `RouteCondition.before(...)`, `after(...)` and `between(...)`, which read the `java.time.Clock` bean if there is one, otherwise the system clock, like the conditions of the ordinary routes;
* their combinations with `all`, `any`, `not`, `and`, `or` and `negate`.

Two conditions are rejected, with an `IllegalArgumentException` when they are given to the route, so that the application fails to start with a message that names the route and the condition:

* a condition of a lambda, `RouteCondition.custom(...)` or `where(Predicate<HttpRequest>)`, as it receives the api:http.HttpRequest[], which a direct route never creates;
* `RouteCondition.remoteAddress(...)`, as it resolves the client address with the api:http.server.util.HttpClientAddressResolver[] of the server, from the request and its forwarded headers. `peerAddress(...)`, which reads the connection only, is the condition for a direct route.

=== Runtimes

The Netty server answers direct routes, synchronous and asynchronous. An application that declares a direct route on a runtime that does not, e.g. a serverless function runtime, fails to start with a message that says so: a direct route is never served as an ordinary route, which the filters it was declared to skip would see. A runtime that answers direct routes answers the asynchronous ones too: one that cannot hold a request without a thread waits for the stage on a worker thread, and may then not cancel it when the connection closes.

[[functionalRoutesDirectRuntimes]]
Another server runtime that answers direct routes writes the response as it is too, but may add a header it cannot leave out: some always add a `Date` header, or a `Server` header when configured to. A `Date` or `Server` header the route sets replaces the runtime's where the runtime allows it. The reason phrase of the status is written where the runtime lets it be set, and a compressed direct response may be sent chunked and carry a `Vary` header.

=== Implementing direct routes in a server runtime

The package pkg:web.router.direct[] is the experimental SPI between the router and a server runtime, e.g. a servlet container:

* the runtime declares a api:web.router.direct.DirectRouteSupport[] bean, which tells the router that direct routes are answered: without one, an application that declares a direct route fails to start. Every runtime that declares it answers the asynchronous direct routes too, as described below. Its two methods have defaults: `shareableBody(Object)` prepares the body of a response given as a value, which the requests of the route share, so a runtime that consumes a body of its own type when it writes it, e.g. releases a buffer, returns a copy it can write for every request, and releases the body; `discard(HttpResponse)` releases the body of a response the runtime never writes, one an asynchronous route completed after its response was cancelled;
* when it starts, it gets the api:web.router.direct.DirectRouteLookup[] bean, if there is one and it is not empty, and skips the lookup otherwise;
* for each request it receives and decodes without an error, before it creates the api:http.HttpRequest[] or runs anything else, it calls `match(DirectRequest)`, on the thread that received it. A request its decoder failed on is answered with its error as usual, never by a direct route. The runtime may validate the target and the query lazily, and throw an api:web.router.direct.InvalidDirectRequestException[] from the `DirectRequest` when it finds them invalid: the lookup then matches no route, and a route whose function reads the invalid query declines the request, so the runtime answers it on its ordinary path, e.g. with `400`. The lookup reads the path only for a method that has direct routes. The api:web.router.direct.DirectRequest[] reads its own request: the method, the raw path without the query, of an absolute-form request target too, the headers, the query parameters, decoded like the parameters of its requests and only when a condition or a function asks for them, and the address of the peer;
* when `null` is returned, it handles the request as usual, with its body untouched;
* when a `DirectMatch.Sync`, see api:web.router.direct.DirectMatch[], is returned, it calls its `respond(HttpResponseFactory)` with its own api:http.HttpResponseFactory[], on the same thread, so that the responses the router creates, e.g. the copies of a response given as a value, are of its own type. When `null` is returned, the route declined the request: it handles the request as usual, with its body untouched. When a response is returned, it discards the body of the request and writes the response: exactly its status, its headers and its body, with only the framing the protocol needs, the `Content-Length` of the body and the handling of the connection, and the `Date` and `Server` headers the server is configured to add, unless the route set them, and no other header of its own that it can leave out; the headers only for a `HEAD` request, with the `Content-Length` of the body, or the one the route set when it has no body. A `Date` or `Server` header it always adds is replaced by the route's where it allows it, and the reason phrase is written where it can be set. A body that is not bytes or text is written by the message body writer of the content type of the response, `application/json` if it has none. A response of another type than its own is converted;
* it honours `MessageBodyWriter.isBlocking()`, see api:http.body.MessageBodyWriter[]: the response `respond` returns is written on the thread that received the request, so it refuses a blocking writer and answers `500`, and it runs the blocking writer of the response of an asynchronous route off its event loops;
* when a `DirectMatch.Async` is returned, the matched route is asynchronous: the runtime calls its `respondAsync(HttpResponseFactory)`, which starts the route, on its executor if it has one, and returns its response as a `CompletableFuture`. The route was matched once, and its constraints and conditions evaluated once. The runtime holds the request, without reading or discarding its body, until the response completes, then writes it as above, or handles the request as usual, with its body untouched, when it completes with `null`. It writes the responses of a connection in the order of its requests, cancels the response when the request is abandoned, as the connection closes or, for a multiplexed protocol, the stream of the request is reset, and answers a failed response with `500`. A runtime that cannot hold a request without a thread waits for the response on a worker thread, never on the thread that reads the connection.

The lookup allocates little: `match` allocates nothing for a route that answers with a value, whose match is created once, and for a route whose function composes the response only its match, which is the `DirectContext` of the function, with the path variables created when a constraint or the function reads them. A request whose method has no direct route is not even parsed: its path is not read.
