=== Conditions and order

`where(RouteCondition)`, on a route or a group, matches only the requests that meet the condition, like `@RouteCondition` on a controller method. api:web.router.builder.RouteCondition[] builds declarative conditions on the headers, query parameters, cookies and method of a request, its host and client address, and the time it arrives, and combines them with `all`, `any`, `not`, `and`, `or` and `negate`.

snippet::io.micronaut.docs.server.functional.ConditionRoutes[tags="where", indent=0, title="A route for the requests that meet a condition"]

<1> The route matches the requests with an `X-Beta` header or a `beta=true` query parameter. The conditions of the groups of a route and those of the route must all be met, and so must several conditions of a route or a group.
<2> A request both routes match is ambiguous: they have the same URI template. The route with the lowest order wins.
<3> The route for the other requests, with the default order `0`, the order of controller routes.

A request that the conditions of a route reject is answered as if the route did not exist: by another route, or with `404`, never with a `405`, `415` or `406` of the rejected route. The conditions run while the request is matched, for every request to the path of the route, so they must be fast, must not block and must not read the body.

A condition compares a value with a api:web.router.builder.ValueMatcher[]: `equalTo`, `startsWith`, `endsWith`, `contains`, `oneOf`, `regex`, which matches the whole value, and `present`, each case-sensitive unless made to `ignoringCase()`, and combined with `and`, `or` and `negate`. A matcher compares the value in place, without decoding or copying it: a cookie is found in the `Cookie` header without decoding the other cookies. An absent value, e.g. a request without the header, is given to the matcher as absent: only a negated matcher, like `present().negate()`, matches it.

snippet::io.micronaut.docs.server.functional.ConditionRoutes[tags="matchers", indent=0, title="Conditions with matchers"]

<1> A header of one of the values, ignoring case, or a cookie of the value.
<2> The address of the peer of the connection in one of the IPv4 or IPv6 ranges, in CIDR notation: `peerAddress(...)` never reads a forwarded address, so a client cannot spoof it. An address is never looked up by name.
<3> A request from an instant on: `before(instant)`, `after(instant)` and `between(start, end)` read the `java.time.Clock` bean if there is one, otherwise the system clock.
<4> A path variable constrained with a matcher, see below.

The host of `host(...)`, compared ignoring case and without the port and a final dot, is the host as the api:http.server.util.HttpHostResolver[] of the server resolves it, which reads a forwarded host only as `micronaut.server.host-resolution` configures it.

There are two conditions on the address of a client. `peerAddress(...)` reads the address of the peer of the connection only, never a header: use it for access control, e.g. an allow or a deny list. `remoteAddress(...)` reads the address as the api:http.server.util.HttpClientAddressResolver[] resolves it: from the header that `micronaut.server.client-address-header` names, or else from the `Forwarded` and `X-Forwarded-For` headers of the request, or else the peer of the connection. Without that property any client can send those headers and choose its address, so `remoteAddress(...)` is right only behind a trusted proxy that sets the configured header, where the peer is the proxy and the header is the client.

The router normalizes the conditions of a route when it builds the route: the conditions of its groups and its own become one condition, nested `all` and `any` are flattened, double negations and duplicates are removed, and the parts are ordered cheapest first: the methods, then the lookups of a value and the time, then the prefixes, suffixes and parts, then the regular expressions and the host and the client and peer addresses, which cost the same and keep the order they were declared in, and last the conditions of lambdas, in the order they were declared, outer group first. The evaluation stops at the first part that decides. A condition is data that only the router evaluates, with the host and client address resolvers of the server and the clock of the application: it is not a `Predicate`. `RouteCondition.custom(predicate)`, or `where(Predicate<HttpRequest<?>>)`, takes a lambda for what the other conditions do not express; the lambda is given the request as it is, e.g. its `Host` header rather than the host the server resolves, and `RouteCondition.custom(...)` makes a lambda a condition to combine with `and`, `or`, `all` and `any`. api:web.router.builder.RequestPredicates[] has shorthands of these conditions, and `accept(...)` and `contentType(...)`, which compare media types with their wildcards and are conditions of lambdas.

The order only breaks a tie between routes that are equally good for a request. Among the routes that match a request, the router first keeps the routes that explicitly produce the media type the request accepts first, then, for a request with a body, the routes that explicitly consume its `Content-Type`, then the routes with the most specific URI template. It then prefers a route of the request's method over a route of `any(...)`, and an explicit `HEAD` route over an implicit one, and only then compares the orders: the order never makes a less specific route win, and an `any(...)` route never wins over a route of the request's method, whatever their orders. Routes left with the same order still make the request ambiguous, which is answered with `400`. A group's order applies to its routes, and a route's own order overrides it.

The order is global: it is compared between any routes left for a request, controller routes and the routes of every `HttpRoutes` bean and group alike, and the lower order wins. Controller routes have the order `0`, so a handler route with a negative order wins a tie with a controller route, and one with a positive order loses it. The order of an `HttpRoutes` bean, e.g. `@Order` on the bean, orders the beans, not their routes.

=== Path variable constraints

`constrain(...)`, on a route or a group, matches only the requests whose path variables the constraint accepts. A request the constraint rejects is not a match of the route, as if its URI template did not match: another route on the same path answers it, or it is answered with `404`.

snippet::io.micronaut.docs.server.functional.ConditionRoutes[tags="constrain", indent=0, title="Routes for some values of a path variable"]

<1> The routes of the group match the known shops only, the values of the `SHOPS` set: `/shops/west/stock` is answered with `404`.
<2> The variable converted to a type: a value that does not convert, like `lamp`, or that the predicate rejects, like `-1`, is not a match. The order breaks the tie with the other route for the values both accept.
<3> The route for the other values.

The forms are `constrain(Predicate<PathVariables>)`, `constrain(variable, Predicate<String>)`, `constrain(variable, type, Predicate<T>)`, `constrain(variable, Collection<String>)`, `constrain(variable, ValueMatcher)` and `constrain(Map<String, ValueMatcher>)`. A variable without a value, a value that does not convert and a predicate that throws all reject the request; the exception is logged at `DEBUG` level. A matcher is given a variable without a value as an absent value, which only a negated matcher accepts.

The constraints run while the request is matched, right after the URI template of the route matched, before the media types, the conditions of `where` and the ambiguity between routes. The methods allowed for a `405`, the media types for a `415` or `406`, CORS preflight requests and implicit `HEAD` routes consider only the routes whose constraints pass, so a rejected value never produces a `405`. The constraints of the groups of a route, outer group first, and of the route must all pass. Like conditions, constraints must be fast and must not block; a route without constraints costs nothing more to match.

=== Attributes

`attribute(name, value)` gives a route, or every route of a group, metadata that the code handling its requests reads from the matched route: the handler, route filters, server filters and `@ServerFilter` beans (with a api:web.router.RouteInfo[] parameter, or with `RouteAttributes.getRouteInfo(request)`).

snippet::io.micronaut.docs.server.functional.ConditionRoutes[tags="attributes", indent=0, title="Route attributes"]

<1> Every route of the group has the attribute.
<2> A filter reads the attribute of the matched route.
<3> An attribute of a route overrides the attribute of its group.

The attributes are the attributes of the route, not of the request. The map is read-only and its values are never `null`.

=== Ports

`port(int)`, on a route or a group, routes the requests on that port only, like `@Controller(port = ...)`: the server opens the port when it starts, and a request on another port is answered as if the route did not exist, with `404`.

snippet::io.micronaut.docs.server.functional.ConditionRoutes[tags="port", indent=0, title="Routes on another port"]

<1> The routes of the group match the requests on the management port only.

`port(String)` takes the port like the `port` member of `@Controller`: a number, or property placeholders with defaults, e.g. `port("${my.admin.port:8081}")`, resolved with the environment of the application when the routes are declared. A placeholder that cannot be resolved fails the startup, like for a controller, and a port that is not a number between `1` and `65535` is rejected.

Once a route of the application has a port, the routes without one match the requests on the default ports of the server only.
