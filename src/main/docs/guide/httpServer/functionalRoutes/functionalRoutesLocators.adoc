A locator routes a path prefix to a target found at request time, such as a shop selected by a path variable. An api:web.router.builder.LocatedRoutes[] declares that target's routes relative to the prefix. Its handlers receive the target as an additional argument.

snippet::io.micronaut.docs.server.functional.LocatorRoutes[tags="imports,clazz", indent=0, title="Locator routes"]

<1> Reuse one `LocatedRoutes` instance for a target type. Its route definitions are built once and shared across targets.
<2> `locate(prefix, locator, routes)` finds the target. Here `/shops/north/items/1` reaches `/items/{index}` with both prefix and route variables available.
<3> Use `locateAsync` when finding the target returns a `CompletionStage`.
<4> A function can choose the `LocatedRoutes` for each target, for example according to its type.
<5> `targetType()` declares the target type expected by the handlers.
<6> Declare relative routes with handlers such as `(request, pathVariables, shop) -> ...`. A route at `/` matches the locator's prefix. Nested groups and local error routes are supported.
<7> Handlers without a target parameter can retrieve it with `LocatedRoutes.locatedTarget(pathVariables, type)`.

=== Matching and Execution

The locator runs at most once per request. A `null` target produces `404`; exceptions use normal error handling, starting with the locator's groups.

Once a target is selected, routing continues within its routes. If none matches, the response is `404`, `405`, `415` or `406` as appropriate. The request does not fall back to unrelated application routes.

Synchronous locators run during route matching, typically on the event loop, and must not block. Use `locateAsync` for asynchronous work. The server stops waiting if the client disconnects, without cancelling the returned stage, which may be shared.

=== Groups and Settings

Located routes inherit filters, annotations, attributes, media types and executors from the groups enclosing the locator. Their own settings and groups can override these defaults. Filters run from the enclosing locator groups inward to the matched route.

Located routes can contain further locators. They cannot declare server filters, global error or status routes, dedicated ports, WebSocket routes or static resource routes. Declare those on the application builder instead.

=== Locators That Read the Body

Use `locator(prefix)` followed by a body stage when finding the target requires request data:

snippet::io.micronaut.docs.server.functional.FormLocatorRoutes[tags="imports,clazz", indent=0, title="A locator that reads the form"]

<1> Start a locator that reads the body.
<2> Choose `form()`, a decoded `body(type)`, or `body()` for an api:http.body.AsyncRequestBody[].
<3> The locator runs when the body is ready, usually on the event loop. Use `locateAsync` for work that completes later.
<4> The located route can read the form too; it receives the same collected form and files.
<5> A form locator receives `FormData.empty()` for a non-form request without reading its body. A malformed form fails the request.

Body-reading locators use a copy of the body and buffer it within `micronaut.server.max-request-buffer-size`. Larger bodies produce `413`. A decoded body is required unless its type is nullable.

NOTE: Form locators require a server that supports decoding forms from a copy of the request bytes, such as Netty. They are not supported on servers without that capability, such as servlet containers.
