You may need to resolve the host name of the current server. The Micronaut framework includes an implementation of the api:http.server.util.HttpHostResolver[] interface.

The default implementation looks for host information in the following places in order:

. The configured host, protocol and port headers. When any of them is configured, no other header is read: a missing value comes from the request URI or the embedded server, and the two properties below do not apply.
. The `Forwarded` header, if `micronaut.server.host-resolution.allow-forwarded` is `true`. When enabled and present, `Forwarded` takes precedence over the `X-Forwarded-*` headers even if it has no `host` parameter.
. The `X-Forwarded-Host`, `X-Forwarded-Proto` and `X-Forwarded-Port` headers, if `micronaut.server.host-resolution.allow-xforwarded` is `true` and `X-Forwarded-Host` is present.
. The `Host` header
. The properties on the request URI
. The properties on the embedded server URI

Both properties default to `false`. Enable a header family only behind a trusted proxy that overwrites or removes those headers. The environment variable for `allow-xforwarded` is `MICRONAUT_SERVER_HOST_RESOLUTION_ALLOW_XFORWARDED`. Micronaut silently ignores the spelling `allow-x-forwarded` and its environment variable `MICRONAUT_SERVER_HOST_RESOLUTION_ALLOW_X_FORWARDED`.

The behavior of which headers to pull the relevant data can be changed with the following configuration:

include::{includedir}configurationProperties/io.micronaut.http.server.HttpServerConfiguration$HostResolutionConfiguration.adoc[]

The above configuration also supports an allowed host list. Configuring this list ensures any resolved host matches one of the supplied regular expression patterns. That is useful to prevent host cache poisoning attacks and is recommended to be configured.
