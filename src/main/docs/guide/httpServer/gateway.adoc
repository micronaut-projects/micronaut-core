The `micronaut-http-gateway` module relays requests to upstream servers: routes declared in code or in the configuration, with the predicates and filters of Spring Cloud Gateway, load balancing over the services of the service discovery, retries and circuit breakers. A gateway route is an ordinary <<functionalRoutes, functional route>>: the server filters, e.g. of security and CORS, the error routes, and the precedence of more specific routes apply to it like to any route. The module and all its API are experimental.

dependency:io.micronaut:micronaut-http-gateway[]

The gateway runs on the Netty server and relays with the raw HTTP client, so an HTTP client implementation must be on the classpath too, e.g. `micronaut-http-client`.

== Routes in Code

A bean of api:http.gateway.GatewayRoutes[] declares routes with a api:http.gateway.GatewayRouteBuilder[]:

snippet::io.micronaut.docs.server.gateway.ApiGateway[tags="imports,clazz", indent=0, title="Gateway routes in code"]

<1> The URI of the upstream, here from the configuration
<2> The path pattern: the prefix and every path under it
<3> A condition of the functional routes the gateway route becomes
<4> The filters: `StripPrefix=1` relays `/api/orders/7` as `/orders/7`
<5> The retries, see below

The URI of a route is `http://host:port[/base]`, `https://...`, `ws://` or `wss://` (the same as `http://` and `https://`: every route relays WebSocket upgrades), or `lb://service-id`, a service whose instances the load balancer of the service selects, with the client configuration `micronaut.http.services.<service-id>.*`. A base path of the URI, or of an instance, is put before the path of each request.

A route relays the upgrades to WebSocket only, by default: once the upstream switched protocols, the bytes of the connection pass the filters, the limits and the rate limits of the route as they are. `upgradeProtocols(...)` (`upgrade-protocols` in the configuration) names the protocols a route relays, none to relay no upgrade; a request for another protocol is relayed as a plain request, without its `Upgrade` header.

The path patterns are URI templates of the router, e.g. `/api/orders/{id}`, or the patterns of Spring Cloud Gateway: `/prefix/**` for the prefix and every path under it (never `/prefixX`), `*` for one segment, and `{name}` for a segment captured as a variable. A route without a path pattern matches every path.

=== How Gateway Routes Become Routes

The gateway declares each gateway route as ordinary functional routes of any HTTP method, see <<functionalRoutes, Functional Routes>>, which are routed among the other routes of the application, controller routes included:

* A path pattern of the router, e.g. `/api/orders/{id}`, or with `*` or `{name}` segments, is an exact template: `any(template)`. The handler receives the variables of the template, a variable named `path` included.
* A prefix pattern, `/prefix/**`, is the prefix and every path under it: `any(prefix)` and `any(prefix + "/{+path}")`. The prefix itself must not have a variable named `path`, which is the rest of the path: a gateway route with such a pattern fails the startup.

Every route consumes and produces every media type, takes the WebSocket upgrades that no WebSocket of the server takes, which the upstream switches the protocols of, and sends the error responses of the upstream as they are, see `keepErrorResponses()` in <<functionalRoutesErrors, Error and Status Routes>>: a `404` or a `500` of the upstream is relayed with its body and headers, whatever global or group status routes the application has. The failures of the gateway itself, e.g. a `502` for an upstream that cannot be reached, a `504` for a response timeout or a `503` for an open circuit breaker, are exceptions, an api:http.gateway.UpstreamException[], which the error routes, the exception handlers and the status routes of their status answer as for any other route. The response of a circuit breaker fallback is returned, and is relayed as it is.

The path of the upstream request is the path of the request as the client sent it, percent-encoded, e.g. `/a%2Fb`, never the decoded value of a variable: a path filter rewrites the raw path, see the filters below, and its variables are the raw values of the variables of the pattern. A gateway route keeps the whole path by default, e.g. `/api/orders/1` reaches `/api/orders/1` of the upstream; `StripPrefix=n` removes the first segments, e.g. `StripPrefix=2` relays `/api/orders/1` as `/1`, and `PrefixPath` and `RewritePath` change it further.

The order of the routes follows the router: of the routes that match a request, the most specific one answers, e.g. a controller route `/api/orders/special` before the gateway route `/api/orders/**`, and A route of the method of a request, e.g. a `GET` route of the application, answers before a gateway route of the same template, whatever their orders: the gateway routes are routes of any method. The `order` of a gateway route, or of any route, only breaks a tie between routes that match equally well, the lower order first. The order of the api:http.gateway.GatewayRoutes[] and api:web.router.builder.HttpRoutes[] beans only decides the order the routes are declared in. A WebSocket route of the application, a api:websocket.annotation.ServerWebSocket[] or a WebSocket route of the functional routes, takes an upgrade request before a gateway route of the same path.

=== Proxy Handlers on Ordinary Routes

A gateway route declared with api:http.gateway.GatewayRoutes[] or in the configuration has its conditions, order, weights, default filters and the route filters of its gateway filters, see `GatewayFilter.configure(...)`. To relay the requests of an ordinary route of the application instead, e.g. in a group of routes with filters or security annotations of its own, create the api:http.gateway.ProxyHandler[] of a gateway route with the api:http.gateway.ProxyHandlerFactory[] and route to it like to any asynchronous handler:

snippet::io.micronaut.docs.server.gateway.OrderRoutes[tags="imports,clazz", indent=0, title="A proxy handler on ordinary routes"]

<1> The handler of a gateway route, which is not registered itself
<2> The routes of the application that relay to it

Such a route is not a gateway route: the conditions, the order, the weights, the default filters and the route filters of the gateway route do not apply, only its upstream, its retries, its circuit breaker, its timeouts and the proxy transforms of its filters, which the handler applies. The route is the application's: it decides the media types, whether the error responses of the upstream replace the ones of its status routes, with `keepErrorResponses()`, and the paths it routes, e.g. `any(prefix)` and `any(prefix + "/{+path}")` for a prefix.

The gateway is a reverse proxy: it relays each request to a server of its own choice, the upstream of the route, and the client does not know it. To call another service from the code of a route, e.g. to forward a request to a local server and use its answer, use the api:http.client.ProxyHttpClient[], or a declarative client with ann:http.client.annotation.Client[], which are not gateway routes either.

== Routes in the Configuration

[configuration]
----
micronaut:
  gateway:
    default-filters:
      - AddResponseHeader=X-Gateway, mn
    routes:
      orders:
        uri: lb://orders
        order: 10
        response-timeout: 5s
        predicates:
          - Path=/api/orders/**
          - Header=X-Tenant, \w+
          - Method=GET,POST
        filters:
          - StripPrefix=2
          - name: Retry
            args:
              retries: 2
              statuses: BAD_GATEWAY, SERVICE_UNAVAILABLE
          - CircuitBreaker=orders, ordersFallback
        metadata:
          team: orders
----

Predicates and filters are given in the shortcut syntax, `Name=arg1, arg2`, or by `name` and `args`. They are created by the beans of api:http.gateway.config.GatewayPredicateFactory[] and api:http.gateway.config.GatewayFilterFactory[] named after them, e.g. `@Named("StripPrefix")`: an application adds its own predicate or filter with a bean of its name. The arguments bind by position or by name, through the conversion service or to the constructor of an introspected record, without reflection. An unknown predicate or filter, an invalid argument, or a route without a URI fails the startup with the id of the route; a route with `enabled: false` is not registered. The routes of the configuration are a map keyed by their ids, so the order they are written in is not an order of the routes: the `order` of a route breaks the ties, see above.

The predicates are `Path`, `Method`, `Header` (a regular expression matches the value or one of its comma-separated elements), `Query`, `Cookie`, `Host` (`**.example.org`, `{sub}.example.org`), `RemoteAddr` (the peer of the connection), `XForwardedRemoteAddr` (the client address of `X-Forwarded-For`, see below), `After`, `Before` and `Between`.

== Dynamic Routes

The routes of api:http.gateway.GatewayRouteLocator[] beans can change while the application runs. They are loaded at startup and again on every refresh: `POST /gateway/refresh` of the gateway endpoint, a `RefreshEvent`, or every `micronaut.gateway.refresh-interval`. A refresh replaces them all at once; a refresh that fails, or that gives an invalid route, keeps the last routes. A request is relayed by the routes it was matched with, also when a refresh replaces them while it runs, and the states of the circuit breakers and of the outlier detection survive a refresh. The routes of the locators come after the other routes, and never shadow them.

NOTE: A refresh builds the routes of the locators again, with their filters. The state of a filter lives in the filter: a `RequestRateLimiter` of the configuration shares one in-memory limiter whose buckets are keyed by the route, so its buckets survive a refresh, but a locator that builds a `GatewayRateLimit`, a `Bulkhead` or a response cache in code each time starts them empty. Such a locator keeps its filter instances, or the rate limiter they use, from one refresh to the next.

* `micronaut.gateway.route-repository.enabled: true` adds an api:http.gateway.InMemoryGatewayRouteRepository[] to save and delete routes in code; `DELETE /gateway/{id}` deletes one.
* `micronaut.gateway.discovery-locator.enabled: true` gives each service of the discovery client a route: `/<service-id>/**` to `lb://<service-id>`, without the prefix, like Spring Cloud Gateway's discovery locator. `include-pattern` (a regular expression of the service ids), `lower-case-service-id`, `route-id-prefix` and `uri-template` (`lb://{serviceId}`) configure it; set a `refresh-interval` to follow the services.

== Filters

The api:http.gateway.GatewayFilters[] are the proxy transforms, applied once to the upstream request before the first attempt and to the upstream response while its body streams, and the route filters:

* the path: `StripPrefix`, `PrefixPath`, `SetPath`, `RewritePath`;
* the headers of the request: `AddRequestHeader`, `AddRequestHeadersIfNotPresent`, `SetRequestHeader`, `RemoveRequestHeader`, `MapRequestHeader`, and of the response: `AddResponseHeader`, `SetResponseHeader`, `RemoveResponseHeader`, `RewriteResponseHeader`, `DedupeResponseHeader`, `RewriteLocationResponseHeader`;
* the query: `AddRequestParameter`, `RemoveRequestParameter`;
* the host: `PreserveHostHeader`, `SetRequestHostHeader`;
* the route filters `SetStatus`, `RedirectTo` and `SecureHeaders`, which apply to every response of the route, including a fallback or an error of the gateway;
* the size limits: `RequestSize` (`413` with an `errorMessage` header for a `Content-Length` over the limit, before the upstream is called; a body that streams in fails the relay with `413` once it goes over, while no response was relayed) and `RequestHeaderSize` (`431` when the names and values of the headers, cookies included, are larger than the limit, or when there are more headers than an optional count);
* the body filters `ModifyRequestBody` and `ModifyResponseBody` (a `BodyRewriter`, in code or as a named bean), `RemoveJsonAttributesResponseBody` (needs a `JsonMapper`), and `ReadBody` (a named `Predicate<byte[]>` bean in the configuration): they read the whole body, up to a limit (256 KiB by default in the configuration), decode `gzip` and `deflate`, and send the result encoded again with its new `Content-Length`. **A route with a body filter no longer streams that body**, its response trailers are dropped, and a body over the limit is `413` for a request and `502` for a response. `ReadBody` runs once the route is chosen: a body that does not match is answered with `404`, no other route is tried;
* `CacheRequestBody`, which reads a copy of the body, up to a limit, into `GatewayRequestContext.cachedRequestBody()` for the other filters; the body is still relayed;
* `Retry` and `CircuitBreaker`.

The path filters work on the raw, percent-encoded path, which they never decode: the rest of the path and the query are relayed byte for byte, and `SetPath` and `PrefixPath` put in the variables as the client sent them. A header value may use the path variables, e.g. `{segment}`; a value that would carry a line break answers `400`. The inbound request, which the server filters see, is never changed.

== Weights and Canaries

Routes with the same paths in a weight group split the traffic by weight, like Spring Cloud Gateway's `Weight` predicate: `.weight("orders", 9)` in code, `Weight=orders, 9` in the configuration. For each request the group chooses one of its routes, at random by weight, and only that route matches. A route of weight `0` only takes requests forced to it. The group can be set up under `micronaut.gateway.weight-groups.<group>`:

[source,yaml]
----
micronaut:
  gateway:
    weight-groups:
      orders:
        override-header: X-Canary # a request with X-Canary: orders-v2 goes to the route orders-v2
        sticky-header: X-User     # the same user always gets the same route
    routes:
      orders-v1:
        uri: lb://orders-v1
        predicates: [ "Path=/orders/**", "Weight=orders, 9" ]
      orders-v2:
        uri: lb://orders-v2
        predicates: [ "Path=/orders/**", "Weight=orders, 1" ]
----

== Response Cache

`GatewayFilters.localResponseCache(timeToLive, size)` (`LocalResponseCache=30m, 16MB` in the configuration) caches the `200` responses to `GET` requests in the memory of the gateway, like Spring Cloud Gateway's `LocalResponseCache`, and answers `GET` and `HEAD` requests from it:

* a response is fresh for its `s-maxage`, `max-age` or `Expires`, or for the time to live when it has none; it is served with an `Age`, and a matching `If-None-Match` or `If-Modified-Since` gets a `304`;
* the key is the route, the path and the query, the `Authorization` and `Cookie` of the request, and the values of the headers of the `Vary` of the response;
* `no-store`, `private` and `no-cache` responses, responses with `Set-Cookie` or `Vary: *`, and responses to a request with `Authorization` (unless `public` or `s-maxage`) are not stored, and remove what is stored for the URI; a `POST`, `PUT`, `PATCH` or `DELETE` of the URI removes its responses;
* a request with `no-cache`, `max-age=0` or `Pragma: no-cache` goes to the upstream, a request with `no-store` is not stored; `Range` requests and protocol switches bypass the cache;
* the body is copied while it streams to the client, which is never slowed down by the copy; a response that does not complete, or is larger than the size, is not stored.

The responses are kept by a api:http.gateway.ResponseCacheStore[]: api:http.gateway.InMemoryResponseCacheStore[] by default, least recently used out first, or a bean named in `store`, e.g. one backed by micronaut-cache. A cache lock for concurrent misses and serving stale responses on errors are not supported.

== Rate Limits and In-Flight Limits

A api:http.gateway.GatewayRateLimit[] (`RequestRateLimiter` in the configuration) is a token bucket per key of a request, like Spring Cloud Gateway's: `replenish-rate` tokens a second, up to `burst-capacity` (at least the rate; `0` denies every request), `requested-tokens` per request. A request over the limit is answered with `429` without calling the upstream, and the responses carry `X-RateLimit-Remaining`, `-Replenish-Rate`, `-Burst-Capacity` and `-Requested-Tokens` (`include-headers: false` turns them off). A request without a key is answered with `403` (`deny-empty-key`, `empty-key-status`). The key comes from a api:http.gateway.KeyResolver[]: `remoteAddress` (the default: the peer, or the client behind the trusted proxies of `micronaut.gateway.forwarded.trusted-proxies`; an IPv6 client by its `/64` network), `principal`, `header:<name>`, or the name of a `KeyResolver` bean, which is synchronous: it reads the request and does no IO. The buckets are in the memory of the gateway (api:http.gateway.InMemoryRateLimiter[]), at most 100,000: a new key is denied while they are all taken; a api:http.gateway.GatewayRateLimiter[] bean named in `rate-limiter` keeps them elsewhere, and when it fails the request is let through. Each route has its own buckets, also when the limit is a default filter.

[source,yaml]
----
micronaut:
  gateway:
    default-filters:
      - RequestRateLimiter=10, 20, 1, header:X-Api-Key
----

`GatewayFilters.bulkhead(max, keyResolver)` (`Bulkhead=max, key-resolver`) answers `429` for a request of a key that has `max` requests in flight, until their responses are done: a streamed body, an event stream or a switched connection counts until it ends.

== Load Balancing, Retries and Circuit Breakers

A `lb://` route selects an instance for each attempt, leaving out the instances it already tried, and the exchange reports its outcome to the load balancer of the service, so that its outlier detection (`micronaut.http.services.<id>.outlier-detection.*`) ejects a failing instance.

A api:http.gateway.GatewayRetry[] sends a request again only when it can: the body has been fully received, there is none, or it is kept while it streams in (for a retried method, up to `maxReplayBytes`, 1 MiB by default, `max-replay-bytes: 64KB` in the configuration; a larger body is sent once and the answer relayed), and either the request provably never reached the upstream (for any method), or its method is one of the retried methods (`GET` and `HEAD` by default) and the attempt failed before the headers of a response, or answered with a retried status (`502`, `503` and `504` by default). Nothing is retried once the headers of a response arrived. The delays follow a `RetryPolicy`: `delay`, `multiplier`, `jitter`, and `max-delay`, the limit of their sum. `withExceptions(...)` retries only some failures, e.g. `ReadTimeoutException`, and `withResponseHeader(name, value)` (`response-header`, `response-header-value`) retries a response with a matching header like a retried status. The failure of the last attempt is `GatewayRequestContext.find(request)` and its `failure()`, also for the error routes.

A api:http.gateway.GatewayCircuitBreaker[] guards each attempt with a named circuit of the api:retry.CircuitBreakerRegistry[], shared with the other routes and methods of the name, and configured, e.g. with a rolling window, under `micronaut.retry.circuit-breakers.<name>`. An attempt fails when it cannot reach the upstream or when the response has one of the failure statuses (`failure-statuses`, `500` and above by default); it is reported once the headers arrive, so the circuit never waits for a body. While the circuit is open, when the last attempt failed, or when the response has one of the fallback statuses (`fallback-statuses`, none by default), the fallback handler answers in process, with the failure as `GatewayRequestContext.find(request)` and its `failure()`; without one, the request fails, with a `503` while the circuit is open. A response of a failure status that is not a fallback status is relayed, and only counted.

[configuration]
----
filters:
  - name: CircuitBreaker
    args:
      name: orders
      fallback: ordersFallback # an AsyncRequestHandler or RequestHandler bean of this name
      failure-statuses: 500, 502, 503, 504
      fallback-statuses: 503
----

== Relaying Rules

Where gateways disagree, this one:

|===
|Case |Behaviour

|The upstream does not answer in time (a response or a connect timeout) |`504`
|Connection refused, the name of the host does not resolve, TLS failure, reset or close before the headers, a malformed response |`502`
|A service without an available instance, an open circuit without a fallback |`503`
|A failure after the headers arrived |the connection of the client is cut: the response never ends cleanly
|A path with a dot segment (also encoded), an encoded slash or backslash, a path parameter (`;`), a control character or an invalid encoding |`400`, never relayed: the router matches the raw path, so a path that an upstream could resolve to another path cannot route around the security filters
|`//a///b` |matched and relayed as sent, never read as an authority
|A trailing slash |matches the route without it, like any route, and is relayed as sent
|Several `Host` headers, or a `Host` that is not a host and a port |`400`
|`Host` |the host of the upstream, unless `PreserveHostHeader` or `SetRequestHostHeader`
|Forwarded headers |`X-Forwarded-*` and `Forwarded` are sent (`micronaut.gateway.forwarded.x-forwarded-headers` and `.forwarded-header`); those of a client that is not a trusted proxy (`micronaut.gateway.forwarded.trusted-proxies`, none by default) are replaced, not appended to; `X_Forwarded_For` and the like are dropped; `StripPrefix` sends the prefix it removes as `X-Forwarded-Prefix`; the scheme is `http` or `https`, also for a WebSocket; `X-Real-IP` is relayed only from a trusted proxy
|The client address of `XForwardedRemoteAddr` |the right-most address of `X-Forwarded-For` that is not a trusted proxy, when the peer is a trusted proxy; the peer otherwise
|Redirects of the upstream |relayed, never followed
|A client that goes away before the response |the attempt in flight is cancelled, with its connection to the upstream, and no further attempt is made
|A failure of the upstream |a `502` whose message names the route, not the address of the upstream, which is logged
|Compression |a body is relayed as the upstream sent it: never decompressed, never compressed again, `Content-Length` kept
|Hop-by-hop headers |removed from requests and responses, including the headers `Connection` names, before the gateway adds its own; `TE: trailers` is kept; `Upgrade` and `Connection: Upgrade` are kept for a protocol switch, and `Upgrade` on a `426`; `Upgrade: h2c` is never relayed
|`Expect: 100-continue` |relayed: the client gets the `100` once the upstream asks for the body
|Interim responses (`1xx`) |not relayed, except `100` and `101`
|A malformed request (conflicting lengths, a transfer coding other than chunked) |rejected by the server before any route
|An HTTP version other than 1.0 and 1.1 |`505` over HTTP/1.1, with `reject-unsupported-http-versions`, see below
|A body of unknown length to an HTTP/1.0 client |not chunked: the end of the connection ends it
|Oversized headers or URIs, a huge method |`413` (a huge method a `4xx`), from the server before any route; `RequestHeaderSize` answers `431` for a route
|===

WebSocket and other protocol switches are relayed on the Netty server with an HTTP/1.1 upstream: the response timeout of a route applies to the `101` only, and `activityTimeout` closes an idle tunnel.

== Recommended Server Settings

Some behaviour of the server is decided for a connection, before any route, and is the same for the gateway routes and the other routes of the application. These settings are off by default; a gateway should turn them on:

[configuration]
----
micronaut:
  server:
    http10-keep-alive: true
    reject-unsupported-http-versions: true
----

|===
|Setting |Effect

|`micronaut.server.http10-keep-alive` |an HTTP/1.0 client that sends `Connection: keep-alive` keeps its connection after a response with a `Content-Length`; otherwise the server ends the connection of an HTTP/1.0 client after each response
|`micronaut.server.reject-unsupported-http-versions` |a request of an HTTP version other than 1.0 and 1.1, e.g. `HTTP/9.9`, which the request decoder accepts, is answered with `505` over HTTP/1.1 and the connection closed; otherwise it is served
|===

== The Gateway Endpoint

With the management module present, the sensitive endpoint `/gateway` lists the gateway routes: their upstream, order, paths, predicates, filters, retries, circuit breaker and its state, weight, and the templates of their routes. The values of the header and parameter filters whose names carry credentials, e.g. `Authorization` or `X-Api-Key`, are masked. `/gateway/{id}` gives one route. `POST /gateway/refresh` refreshes the dynamic routes and `DELETE /gateway/{id}` deletes a route of the route repository; the other routes cannot be changed through the endpoint.

== Limitations

* The gateway runs on the Netty server, and is tested there only. It has no Netty code of its own, but a servlet container misses what it relies on, e.g. the streaming of request and response bodies and the relay of a protocol switch: it is not supported on a servlet container.
* The body of a request whose method is not retried is not kept: it is sent again only when no attempt read it, e.g. the connection to the first instance was refused.
* The response timeout of a route counts from the moment the request is sent on the Netty client; on the JDK client it counts from the start of the exchange, the upload included.
* Bytes a client sends after an upgrade request, before the `101`, may be lost; a client must wait for the `101` (RFC 6455).
* A half-close of a switched connection is relayed over plain TCP only: over TLS it closes the connection in both directions.
* A fallback is a handler in the application, or an upstream to fail over to (`fallback-uri`, or a `ProxyHandler` in code): there is no `forward:` URI. It reads the body of the request when no attempt sent it, e.g. while the circuit is open, and the body an attempt sent when it was kept (`maxFallbackBodyBytes`, `max-fallback-body`; 1 MiB for a `fallback-uri`, none otherwise); a larger body is gone.
* A route of a route locator is matched after the others, whatever its order.
